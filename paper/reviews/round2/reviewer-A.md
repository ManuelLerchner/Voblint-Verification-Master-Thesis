# Reviewer A

## Summary

The paper connects source execution, procedure-activation traces, relational calling contexts, side-effecting equations, a previously verified solver, and the report returned by an executable analyzer. The contribution goes beyond another domain formalization: the context coverage interface and the derivation of forward execution coverage from a backward solver certificate are reusable semantic connections. The displayed endpoint theorem agrees with the inspected source. However, the paper's central five-obligation presentation suppresses a stronger return obligation needed for arbitrary graphs, the delivered executable has a custom trusted code mapping absent from the trust-boundary account, and the availability statement leaves reproducibility unresolved. These require revision before publication in JAR.

## Strengths

- **The principal theorem has the promised interface.** Section 5, Theorem 3 (`sections/theorem.tex:38–61`) matches `src/Executable_Surface/CLI/Analysis_Certified.thy:196–208`: a finite source run, a permitted initial store, and `run_voblint config p = Analysed res` imply observation at some node and coverage/verdict consistency at every observed node. The configuration remains universally quantified; the statement does not conceal a separate user-supplied coverage premise.
- **The semantic contract is independent of the numeric implementation.** Theorem 1 (`sections/traces.tex:124–140`) matches `src/Abstract_Interpreter/Framework/Activation/Activation_Backbone.thy:34–49`. Its context-union consequence appears in `src/Program_Model/CFG/Collecting/Activation_Trace_Abstract.thy:268–281`. The explicit separation of relational admission from executable routing gives the framework a purpose beyond collecting existing proofs into one development.
- **The solver connection is a substantive proof-engineering result.** Section 4.3 (`sections/equations.tex:125–131`) accurately summarizes the four assumptions of `src/Abstract_Interpreter/Solver/TD_Solver_Bridge.thy:26–36`, discharged parametrically in the update rule at `src/Abstract_Interpreter/Solver/Globals_Rule.thy:157–165`. The backward-to-forward bridge is present at `src/Analyses/Shared/Result/DG_Live_Unknowns.thy:240–279`; it is not merely assumed at the endpoint.
- **The non-vacuity and necessity claims have specific witnesses.** Section 7 (`sections/evaluation.tex:13–32`) is supported by `src/Examples/Capstone/Example_Non_Vacuity.thy:151–173` and `:581–614`: an analyzed program has two proved checks and an instantiated source guarantee, while a cover satisfying the other four laws fails the desired inclusion when totality is removed. These checks distinguish useful premises from a formally true but empty implication.
- **Verdict qualifications survive source inspection.** Section 5 (`sections/theorem.tex:63–73`) agrees with the collected-state premises of `src/Executable_Surface/CLI/Analysis_Certified.thy:109–148`: neither a refuted check nor an arithmetic error asserts existence of a reaching execution, whereas the dead-check theorem establishes an empty collection. The executable-state refinement cited in Section 6 also exists with its transfer-soundness premise at `src/Abstract_Interpreter/Exec/Refinement/DG_Local_State_Exec_Refinement.thy:266–298`.

## Major weaknesses

1. **The displayed return obligation is not the arbitrary-graph contract that was mechanized.** Section 3.3 says “For a call edge from u into p with continuation k” and then uses “c′ admitted from s” in the Return law (`sections/traces.tex:102–114`). Its explanation identifies that admission with the displayed call. In the actual locale, RETURN quantifies a separate `p'` and `es`, and obtains admission through `admits_call_context`, independently of the return edge into `p` (`src/Program_Model/CFG/Collecting/Activation_Trace_Abstract.thy:58–63`). That predicate existentially chooses a call edge at the same source (`src/Program_Model/CFG/Collecting/Activation_Trace_Context.thy:89–97`). This is a stronger obligation on arbitrary graphs. The return rule only checks the caller and the result procedure against an outgoing call edge; it does not retain the identity of the original edge (`src/Program_Model/CFG/Collecting/Activation_Trace_Def.thy:120–129`). With two outgoing edges, a context admitted through one edge can therefore have to cover a return through another. The artifact explicitly distinguishes this case from compiled graphs: the routed locale assumes `calls_source_unique g` (`src/Abstract_Interpreter/Framework/Context/Routed_Context.thy:52–74`). The paper instead hides this under “side conditions ... on the shape of the graph” in Theorem 2 (`sections/equations.tex:94–95`), while the abstract promises obligations over an arbitrary CFG. State the genuine arbitrary-graph Return law, or explicitly restrict the simplified presentation and prove/explain the restriction. This is a mismatch in the main mathematical interface, not evidence that the checked endpoint is unsound.

2. **The trust-boundary figure omits a custom OCaml hook inside the generated solver.** Section 5 says the handwritten OCaml outside the theorem parses and prints, and Figure 3 lists kernel, code generator, OCaml toolchain, and Zarith (`sections/theorem.tex:75–108`). Yet the export imports `Trace_Run` (`src/Executable_Surface/Codegen/Voblint_Codegen.thy:1–3`), whose code equations install traced solver/report execution (`src/Executable_Surface/CLI/Trace_Run.thy:115–129`). It maps the HOL constant `trace_event` to `Solver_trace_hook.emit` through `code_printing` (`:133–142`). The source explicitly identifies the mapping as trusted and requires the hook to return, raise nothing, and leave solver values alone. Its logical definition is simply unit (`src/Abstract_Interpreter/Solver/Solver_Trace.thy:17–32`). A proved equality involving that logical constant does not verify the handwritten callback. Add this mapping to the executable trust boundary and explain its assumptions, including whether they differ when tracing is enabled. The paper correctly distinguishes proof from target execution elsewhere; the same distinction must cover this project-specific mapping. I found no evidence that the hook actually violates these assumptions.

3. **The availability statement does not identify a reproducible proof artifact.** The Data availability paragraph says that “the vendored solver theories” are archived on Zenodo, then says the development “cannot yet be built from public sources alone” because the originating solver repository is private (`sections/statements.tex:1–7`, frozen submission pp. 14–15). If the complete required theories are in the archive, the upstream repository's privacy should not by itself prevent a build. If they are absent, the archive does not contain what the first sentence promises. For a mechanization whose main contribution is composing this solver with the semantic layers, this ambiguity is material. State exactly what the archive includes, provide the immutable dependency revisions and complete build recipe, and make all required proof inputs accessible to reviewers. I did not verify the external archive contents; their completeness is **UNVERIFIED**. This finding concerns the contradictory publication claim, not an asserted archive failure.

## Minor comments

1. **Expose the strengthened induction invariant.** Section 3.3 describes induction with “every valid trace carries some context” and coverage of its final store (`sections/traces.tex:131–136`). The actual inductive lemma establishes coverage for every member of the caller chain (`src/Program_Model/CFG/Collecting/Activation_Trace_Abstract.thy:212–253`). This strengthening supplies the suspended caller in the return case; an induction hypothesis only about the callee's endpoint would not suffice. Include the chain invariant and explain the context re-selection using totality in `return_covered` (`:183–205`). This would communicate a reusable Isabelle proof insight more effectively than another general statement about locales.

2. **Qualify independence in Figure 2.** Its caption says “Each box is proved without reference to the others” (`sections/equations.tex:29–30`), but routing adequacy explicitly mentions the analysis's enter operation, concretization, solved valuation, and solved set (`src/Abstract_Interpreter/Framework/Context/Routed_Context.thy:86–110`). The useful modularity is that interfaces isolate obligations and generic proofs compose them. The caption currently suggests a stronger independence than the interfaces provide.

3. **Scope the recursion and representation discussion.** “HOL admits only terminating recursion” (`sections/mechanization.tex:51–55`) is too broad for the explanation that follows, which itself uses a domain-predicate encoding. Explain why this particular logical/executable bridge was needed and what the added solver lemma establishes; avoid making a general expressiveness claim about HOL. Likewise, “code generation turns finite sets and maps into lists” (`:56–60`) should be scoped to the chosen code setup, as the proposed alternative libraries already acknowledge.

4. **Clarify the extension claim.** Section 9 says a shared heap would break the assumption that a callee cannot modify its caller's locals (`sections/conclusion.tex:20–24`). A shared heap and pointers into a caller's frame are different changes. Explain which part of the store model or return composition must change for each; shared state does not by itself entail mutation of caller-local variables. As written this is an unsupported limitation argument rather than a demonstrated consequence of the stated assumption.
