## New issues

**N1. The `at_node` example is wrong (§5, p9).** The paper says: "A source configuration does not determine a graph node, since its residual command can occur at several places, as in if (b) {x = 1;} else {x = 1;}. ... In the example, the configuration after either branch is observed at both branch nodes." This holds for the erased residual under the plain simulation. It does not hold for `at_node`, which reads the node off an elaborated run from s0. VIMP expressions are pure and total (§5, p11), so from a fixed s0 the run takes one branch. The regression theory states exactly this: "Without annotations a residual `x = 1` is located in either branch; with them, only in its own" (`Elaborated_Compilation_Regression.thy:12-13`, `raw_residual_left/right` vs `located_residual_determined`, `:17-35`). "After either branch" makes it worse: both branches compile against the same continuation, since `If` "allocates no merge node: both branches receive the same k" (`VIMP_Proc_to_CFG.thy:75`). The example therefore illustrates why elaboration is needed. It does not show that `at_node` is a relation. The non-functionality comes from two runs, or two points of one run, reaching the same erased configuration (the comment at `Elaborated_Compilation.thy:788-789`: "a configuration reachable along two paths"). A loop or an input-dependent branch whose arms converge to the same store would illustrate it. Whichever program the authors choose should be checked in the regression theory; I did not check one. Fix: say the residual alone is ambiguous in this example, elaboration resolves it, and `at_node` remains a relation because distinct runs can reach the same configuration.

**N2. The combine split describes the interface, not the shipped analyses (§4.1, p6).** "combine_env merges the callee's exit state into q, taking the callee's globals, and combine_assign then writes the return value to the call's destination." This is Goblint's intended split, and `dg_spec_combine_transfer` composes the two in that order (`DG_Spec.thy:103-110`). In every shipped analysis, however, `combine_env` is the identity on the resume state, `ls_combine_env = (λ_ _ ci dc de. dc)`, and `combine_assign` performs the entire concrete combine, `ls_combine_assign = (λ_ ci. combine♯ 𝒢 (ci_dst ci))` (`DG_Local_State_Spec.thy:129-130`; template `DG_Spec.thy:525-526`). Since soundness is stated only for the composition (`combine_sound`, `DG_Spec_Sound.thy:348-351`), nothing is wrong formally. The prose should say the interface allows this split and that the shipped analyses do all the work in `combine_assign`.

**N3. The pop rule named is the less common one (§5, p9).** "A call pushes a frame ... and continues with the callee's body followed by a Restore marker; the marker pops the frame and combines the stores as in Section 3 (pstep, rules Call and RestoreStep)." `RestoreStep` fires only when a body falls through to `Restore`. A body that executes `return` (every value-returning procedure, including `bump`) goes through `ReturnSome` → `Unwind`. `UnwindDead` discards the rest of the body, and `UnwindAct` pops the frame with the same combine (`VIMP_Proc.thy:156-166`). Either name `UnwindAct` as well, or write "a return unwinds to the marker, which pops the frame". As written, a reader would trace `bump(5)` through a rule it never uses.

**N4. Scope of the live-set bridge (§4.3, p9).** `sol_vars_callee_result` is proved for the shipped `analysis_spec`, whose enter yields the single alternative `entry_alt`, with `static_resolve` (`DG_Live_Unknowns.thy:197-210`). Theorem 2 itself is generic in multi-alternative enter and in `resolve`. §4.3 should say in one clause that the live-set bridge, and therefore Theorem 3, is instantiated for the single-alternative, statically resolved analyses. A reader can otherwise infer that the overlapping-enter witness of §3.2 also reaches the end-to-end theorem. I asked this as round-3 question 2 (blind A). It is still unanswered in the text.

**N5. The code-generation sentence was not changed (§6, p12).** "code generation turns finite sets and maps into lists that every lookup scans." Write "our code setup represents finite sets and maps as lists". Cuts made for length also removed the sentence on the code equation that stopped recompiling the program at every evaluation. §7 still says "plus one proved code equation" (p13), which now lacks a referent. Restore half a sentence or drop the clause.

**N6. Terminology drift between V, W and "solved".** §4.2 and Table 1 use W ("an unknown of W"), §4.2's adequacy gloss says "solved", and §4.3 distinguishes V from W. In §4.2, "solved" should be "in W" (`Routed_Context.thy:103`). The same applies to "the program entry is in W" vs "solved" in older parts of the text, so check the whole paper.

**N7. The abstract's gloss of post-solution is stronger than what is used.** "every post-solution of the generated, context-routed equations (a valuation that satisfies all of them)" (p1). Theorem 2 needs only a partial post-solution on W (`post_bounded ... vars`, `DG_Ctx_Activation.thy:46-49`), and that is what the solver supplies. The abstract is not false, since a total post-solution satisfies the hypotheses. It does, however, hide the partial-solution step that §4.3 explains as a contribution. Suggest "(a valuation that satisfies them on the unknowns the solver solved)".

**Losses from the cuts.** None changes a formal claim. Removing the `activation_trace` datatype display and the `part_post_solution` display (both present in round 3) is fine, since the prose is accurate. Folding the §6 "Contexts as a relation" paragraph into §3.2 lost the sentence explaining why the entry-state policy needs the relational form beyond overlapping alternatives: it admits no context for excluded stores and proves Total from the solution. §3.3 p6 partly restores this ("an entry-state policy admits no context for stores the analysis has excluded"), which is enough.
