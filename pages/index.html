How it works

Static analysis you can trust, and why

Voblint answers questions about every run of a program without running it, and Isabelle/HOL checks that those answers are right. This page builds up the idea, how the analysis computes its answer, and why an analyzer's own bugs matter.

The idea

What is abstract interpretation?

A test runs a program on some inputs and watches what happens. Abstract interpretation runs it once on descriptions of values, such as “an integer between 0 and 5”, and keeps each description large enough to include every value a real run could produce at that point. If the description at a check satisfies it, every run does.

The vocabulary

What an abstract value stands for

Every abstract value names a set of concrete integers, its concretization γ. Soundness is a statement about those sets: the set for a program point must contain every value a real run has there. A join a ⊔ b is the smallest value whose set contains both, and it may have to take in integers neither side had. Pick a value and watch which integers it covers.

Five domains, five kinds of description

Sign

Seven values from “nothing” to “anything”. Joining 0 and >0 gives ≥0.

Interval

A lower and an upper bound, either of which may be infinite. The one domain here that needs real widening.

Parity

Even, odd, or either. Joining even and odd loses everything.

Congruence

A remainder c modulo m. Modulus 0 means exactly the value c.

Int product

All four at once. A reduction step lets components sharpen one another before a check is decided.

The computation

From a graph to equations to values

The compiler turns a program into a control-flow graph. The analysis turns that graph into equations: one unknown per node, and one term per incoming edge, each applying that edge's action to the value at its source. A solver then finds a value for every unknown. To the rest of the pipeline the solver is a black box: equations go in, one abstract value per node comes out.

Loops: widening and narrowing

A loop can run any number of times, so following it pass by pass may never end. The analysis instead widens: when a bound keeps moving, it jumps straight to infinity, which is safe and ends the climb. It then narrows, using the loop's own guard to pull the bound back. Warrowing combines the two: it widens while a value grows and narrows once it shrinks. Step through it below.

Procedures

Procedures: contexts and globals

Real programs call procedures from several places. Two settings decide how those calls share the solver's work: how the values that several call sites send into a procedure are combined, and how many separate copies of a procedure the analysis keeps apart. Each changes precision, never correctness.

Globals: how contributions to a procedure combine

When several call sites enter the same procedure, each contributes an entry state. The solver treats that entry as a global that the call sites write into, and the Globals setting decides how those writes combine. Below, call site A contributes twice, and its second contribution is smaller than its first.

Which Globals setting should you pick?

No setting is best everywhere. They trade how quickly a growing value is cut off against how much a merged value forgets. Nothing proves any of them terminates on every program: Voblint assumes termination per program, so a bad choice shows up as a run that never finishes, not as a wrong answer.

Start with Warrow

The playground's starting point. Widening is what stops a recursive call whose argument keeps growing.

UNKNOWN with several callers?

Try Warrow per origin. It widens each call site's contribution on its own, so one caller's growth is not blurred into a jump to infinity for all of them. It is not always better: see the last row below.

Join and Join per origin on intervals

Precise when a procedure receives finitely many values, but they never widen: a call chain that keeps growing an argument makes the run spin forever.

If a run does not finish

The analyzer has no timeout. Press Cancel, or change any setting, then pick Warrow or Warrow per origin.

What the papers say
  • Join collects contributions precisely and works well for domains of finite height; with infinite ascending chains, such as intervals, it may not terminate. Tilscher, Graß, Seidl: Verifying a Solver for Mixed Flow-Sensitive Analyses
  • Warrow per origin exists because narrowing one call site's value must not drop what the other call sites contributed. ibid.
  • For local unknowns, a top-down solver with warrowing is always partially correct, and terminates for finitely many unknowns when widening is precise and right-hand sides and dependencies are monotonic; without monotonicity it may not terminate. Bounding the number of switches from widening to narrowing restores termination. Tilscher et al.: Proving Total Correctness of Top-Down Solvers with Widening and Narrowing, Journal of Automated Reasoning 70, 2026
  • Neither paper proves termination for the update rules on side-effected unknowns that these settings select, which is why Voblint's theorems take termination as a premise. The vendored solver also contains a bounded-narrowing rule that this analyzer does not expose.

Context sensitivity: how many copies of a procedure

A context is the key under which a procedure is analyzed. Calls with the same key share one abstract state; calls with different keys stay apart. Here main calls wrap(1) and wrap(4), and wrap calls scale(w) from its single call site s3. The verdicts match what the analyzer reports for the playground's demo program; each mode's Try link opens it with that setting.

The price of precision

Every context is another copy of a procedure to solve. Measured with the analyzer on this site (Interval, Warrow), the number of graph nodes grows with the call-string depth until it matches the program's call depth. More contexts usually buy precision, but not always.

The guarantee

What does “verified” mean?

Analyzers are programs, and programs have bugs. An analyzer bug is worse than most: it reports PROVED for a check that real runs violate, or DEAD for code that runs, and nobody looks again. Mature analyzers track these as their own category; Goblint's issue tracker has a label for them. Voblint's analysis is written in Isabelle/HOL, and theorems there state that its answer contains every real run. Isabelle checks each step of those proofs down to the axioms of its logic.

Where the proof starts and stops

A proof covers a precise statement about precise definitions. Whatever the statement does not mention is trusted: it has to be correct for the guarantee to reach you, but nothing here proves it.

The flagship theorems

Five theorems about run_voblint, the function the analyzer in your browser calls, carry the guarantee. Pick one to see what it assumes and what it proves.

What the theorems do not cover

  • Termination. Assumed per program, as above.
  • Parsing. Lexer and parser are generated from one grammar and tested, not proved. Source ↗
  • Execution. Isabelle's code generator, the OCaml compiler, wasm and your browser are trusted.
  • Presentation. Source positions, rendered strings, badges, the state inspector and GraphViz drawings. OCaml rendering ↗ · page ↗
  • Precision. A correct answer can still be UNKNOWN.

The delivery

From Isabelle to your browser tab

The analyzer you run in the browser is not a reimplementation. Isabelle exports the proved definitions as OCaml, the OCaml is compiled to WebAssembly, and a background worker in the page calls it.

The model

Voblint and Goblint, side by side

Voblint follows the architecture of Goblint, a static analyzer for real C programs, and simplifies wherever a proof would otherwise have to model all of C. The project's own register of differences says what the claim is: “a simplified, machine-checked semantic model of Goblint's interprocedural context-sensitive architecture”, and not the exact implementation.

The fine print

What Voblint can't do, and why proving is hard

A proof is only as wide as its statement. Voblint's guarantee is strong inside a small language and a precise set of assumptions, and this section is about the edges.

A small island in a large language

Goblint analyzes C. Voblint analyzes VIMP, a language small enough that its semantics could be written down and every analysis step proved against it. Hover a region to see what it would take.

What the theorems don't promise

That a run finishes

Every guarantee assumes the solve terminates. Proving that in general is out of scope; for intervals, the join-based rules can indeed run forever.

Precision

There is no completeness claim. A correct result may still say UNKNOWN for a check that holds.

A counterexample

REFUTED says the check fails in every run that reaches it, not that any run does. An error diagnostic likewise does not prove the point is reachable.

Two-way compiler equivalence

The compiler is proved correct in one direction, a forward simulation: every source run is matched in the graph. That is exactly what soundness needs, and no more.

Anything about Goblint's code

Voblint models Goblint's design. No theorem here speaks about Goblint's OCaml implementation.

Why this takes so long to prove

The analyzer that runs is the visible tip. Most of the work is underneath: definitions of what a program means, and proofs that every step respects them.
