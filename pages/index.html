How it works

Static analysis you can trust, and why

Manuel Lerchner Master's thesis, Technical University of Munich Supervised by Alexandra Graß and Helmut Seidl About 30 minutes to read

Voblint answers questions about every run of a program without running it, and Isabelle/HOL checks that those answers are right. This page builds up the idea, how the analysis computes its answer, and why an analyzer's own bugs matter.

Machine-checked theorems connect the source program to the verdicts, and the analyzer in the playground is the code Isabelle exported from the same definitions.

The output

What does it tell you?

Voblint reads a program and answers questions about it without running it. It checks every division for a zero divisor on its own. A verdict about some condition of your own comes from a check you wrote.

The stakes

What if the analyzer is wrong?

Analyzers are programs, and programs have bugs. An analyzer bug is worse than most: it reports PROVED for a check that real runs violate, or DEAD for code that runs, and nobody looks again. Mature analyzers track these as their own category; Goblint's issue tracker has a label for them. Here is one of them, with the verdicts it got backwards. The shorthand in the margins is the analyzer's own state; the next two sections say what it means, and what a machine-checked proof rules out comes after them.

The idea

What is abstract interpretation?

A test runs a program on some inputs and watches what happens. Abstract interpretation computes with descriptions of values instead, such as “an integer between 0 and 5”, and keeps each description large enough to include every value a real run could produce at that point. It iterates until the descriptions stop changing. If the description at a check satisfies it, every run does.

Many runs in, one region per node out

Here is the same idea on a real program, drawn as the part of its control-flow graph from the first branch on: one node per program point, one edge per step between them. Every dot is one run, dropped at the value of x it has at each node it reaches. Switch to the abstract view and the dots give way to the one interval the analysis keeps per node. No interval leaves a dot out, which is soundness. But the runs only ever reach multiples of three, and an interval cannot say so: every band also covers integers no run has. On the left that makes a node look reachable that no run reaches; on the right the guard rules everything out, and the analysis marks the check DEAD. Each check gets a verdict, and each says what the analysis established: PROVED when it shows the check holds in every run that reaches it, REFUTED when it shows the check fails in every such run, DEAD when it shows no run reaches the point at all, and UNKNOWN when the descriptions are too coarse to decide. A check no run reaches can still come out UNKNOWN, as pp4 does here: DEAD says the analysis proved unreachability, not merely that the point is unreachable.

The vocabulary

What an abstract value stands for

Every abstract value names a set of concrete integers, its concretization γ. Soundness is a statement about those sets: the set for a program point must contain every value a real run has there. A join a ⊔ b is the smallest value whose set contains both, and it may have to take in integers neither side had. Pick a value and watch which integers it covers.

Five domains, five kinds of description

Sign

Seven values from “nothing” to “anything”. Joining 0 and >0 gives ≥0.

Interval

A lower and an upper bound, either of which may be infinite. Among the four base domains, the only one that needs real widening; Int inherits it through this component.

Parity

Even, odd, or either. Joining even and odd loses everything.

Congruence

A remainder c modulo m. Modulus 0 means exactly the value c.

Int product

All four at once. Its components sharpen one another after every arithmetic operation and every guard, so four weak facts can decide a check.

Four domains, one value: reduction

An Int value describes the integers all four of its components allow. Each component on its own can miss what another one knows, so the product lets them sharpen one another. A sharpening step never changes that set of integers. It only finds a smaller description of the same set, and a smaller description can decide a check that the larger one could not.

The computation

From a graph to equations to values

The compiler turns a program into a control-flow graph. The analysis turns that graph into equations. In this single-procedure example that means one unknown per node and one term per incoming edge, each applying that edge's action to the value at its source; procedures will key unknowns by node and context. A solver then finds a value for every unknown. To the rest of the pipeline the solver is a black box: equations go in, one abstract value per node comes out.

Watch the compiler take a program apart

The compiler reads a procedure one statement at a time and turns each statement into a numbered node with outgoing edges. Every statement is compiled against the number of the statement after it, so its target is known before it is compiled. The figure replays that walk on the counting loop, with the node numbers and edge labels the real compiler produces.

Loops: widening and narrowing

A loop can run any number of times, so following it pass by pass may never end. The analysis instead widens: when a bound keeps moving, it jumps straight to infinity, which is safe, and for intervals it stops this climb. It then narrows, using the loop's own guard to pull the bound back. Warrowing combines the two: it widens while a value grows and narrows once it shrinks. Step through it below.

What an equation is made of: strategy trees

One level down, the solver never sees ⊔ or assume. It sees each right-hand side as a strategy tree, which spells out every step the evaluation takes: QueryL reads a local unknown, QueryG reads a global one, Side contributes a value to a global, and Answer returns the result. A query does not name its next step directly. It holds a function from the value it reads to the rest of the tree, so the solver finds out which unknowns an equation depends on by running it. Voblint writes these trees in do-notation.

Procedures

Procedures: contexts and globals

Real programs call procedures from several places. Two settings decide how those calls share the solver's work: how many separate copies of a procedure the analysis keeps apart, and how the values that several call sites send into one copy are combined. Each changes precision and whether a run finishes, never soundness.

The life of a call

An analysis does not hard-code what a call does. It supplies three operations: enter builds the callee's entry state from the caller's, a context policy picks which copy of the callee that state goes to, and combine merges the callee's exit state back into the caller. The framework wires them into equations the same way for every domain, and each wire carries its own soundness obligation. Step through the call a = f(2) in a recursive factorial.

Context sensitivity: how many copies of a procedure

A context is the key under which a procedure is analyzed. Calls with the same key share one abstract state; calls with different keys stay apart. Here main calls wrap(1) and wrap(4), and wrap calls scale(w) from its single call site s3. The verdicts match what the analyzer reports for the playground's demo program; each mode's Try link opens it with that setting.

The price of precision

Every context is another copy of a procedure to solve, so the counts below are copies: one per procedure under None, more as the call string grows. Measured with the analyzer on this site (Interval, Warrow), the number of graph nodes grows with the call-string depth until it matches the program's call depth. More contexts usually buy precision, but not always.

Globals: how contributions to a procedure entry combine

When several call sites enter the same copy of a procedure, each contributes an entry state: the side effect in the life of a call. The solver treats that entry as a global unknown that the call sites write into, and the Globals setting decides how those writes combine. The name refers to the solver's global unknowns, not to the program's global variables. Below, call site A contributes twice, and its second contribution is smaller than its first.

Which Globals setting should you pick?

No setting is best everywhere. They trade how quickly a growing value is cut off against how much a merged value forgets. Nothing proves any of them terminates on every program: Voblint assumes termination per program, so a bad choice shows up as a run that never finishes, not as a wrong answer.

Start with Warrow

The playground's starting point. Widening is what stops a recursive call whose argument keeps growing. It cannot stop entry-state contexts from multiplying, though: those need context None or a call string.

UNKNOWN with several callers?

Try Warrow per origin. It widens each call site's contribution on its own, so one caller's growth is not blurred into a jump to infinity for all of them. It is not always better: see the last row below.

Join and Join per origin on intervals

Precise when a procedure receives finitely many values, but they never widen: a call chain that keeps growing an argument makes the run spin forever.

If a run does not finish

The playground has no timeout; the command-line analyzer takes one with --timeout. Press Cancel, or change any setting, then pick Warrow or Warrow per origin, and switch entry-state contexts to None or a call string.

What the papers say
  • Join collects contributions precisely and works well for domains of finite height; with infinite ascending chains, such as intervals, it may not terminate. Tilscher, Graß, Seidl: Verifying a Solver for Mixed Flow-Sensitive Analyses, NASA Formal Methods 2026
  • Warrow per origin exists because narrowing one call site's value must not drop what the other call sites contributed, so narrowing at a global keeps the contributions apart by origin. Stemmler et al.: Taking Out the Toxic Trash, PLDI 2025
  • For local unknowns, a top-down solver with warrowing is always partially correct, and terminates for finitely many unknowns. Total correctness comes from an equivalence that needs monotonic right-hand sides and monotonic dependencies; the paper gives counterexamples for when those assumptions fail. Bounding the number of switches from widening to narrowing restores termination. Tilscher et al.: Proving Total Correctness of Top-Down Solvers with Widening and Narrowing, Journal of Automated Reasoning 70, 2026
  • Neither paper proves termination for the update rules on side-effected unknowns that these settings select, which is why Voblint's theorems take termination as a premise. The vendored solver also contains a bounded-narrowing rule that this analyzer does not expose.
  • More on these solvers under Further reading.

A call that never stops calling

Both settings meet in recursion. f(x) calls f(x + 1) forever, so real runs wind outward on an endless spiral: f(0), f(1), f(2), each turn wider than the last. The analysis has to describe every turn with finitely many contexts, and whether it can depends on the settings: Join and entry-state contexts follow the spiral and never finish, warrowing cuts across it. Switch to the same function stopped at x = 10 and every setting finishes.

The guarantee

What does “verified” mean?

The congruence bug that opened this page is the kind of mistake a proof rules out. Voblint's analysis is written in Isabelle/HOL, and theorems there state that its answer contains every real run. Isabelle checks each step of those proofs down to the axioms of its logic. What that buys is exact, and so is what it leaves out.

Why that bug cannot happen here

VIMP's % is c_mod, which truncates toward zero as C does, and congruence_mod_sound requires c_mod i j ∈ γ of whatever the domain answers. Every transfer carries such a lemma, and run_voblint_check_sound turns them into “a definite verdict holds in every run that gets there”. Congruence alone answers 1+2ℤ, which is sound but too coarse to decide either check; the Int product decides both, because the interval [−1,0] and the odd congruence sharpen each other to −1.

Where the proof starts and stops

A proof covers a precise statement about precise definitions. Whatever the statement does not mention is trusted: it has to be correct for the guarantee to reach you, but nothing here proves it.

The meaning

What a run is: source, graph, trace

Every theorem below is about what a program really does, so “what it does” needs a definition first. Voblint gives three, one per layer. A source step (pstep) rewrites the rest of the program, the store and a stack of caller frames. A graph step (cstep) moves along the compiled control-flow graph and keeps a stack of return points. A trace (valid_ltr) records the path one procedure activation takes and nests its callers and finished callees inside it. The proofs connect the three, one step at a time.

One direction is enough

csim_step: for a well-formed compiled program, whenever the source takes a step, the graph can take zero or more steps and land in a configuration that csim relates to the new one, with the same store. The converse is never proved. Soundness only needs every real run to show up in the graph.

Recursion is nesting

A trace is Root path, Call caller path or Resume caller callee path. The recursive call above builds Call (Call (Root …) …) …, and every activation of f shares the one node exit_f. The trace, not the graph, remembers which activation is which.

Three stacks, one shape

Source frames, graph return points and the trace's chain of callers line up entry by entry. source_run_has_ltr proves it for every run: a source run ending anywhere has a matching graph configuration and a valid trace that ends at the same node with the same store.

The argument

The proof chain: each set inside the next

Soundness is a chain of set inclusions. At one program point, start from the stores real runs have there and widen step by step: the stores the graph's traces reach, then those traces split by context, then what the solver's answer concretizes to. Each link is its own theorem, and the analysis may lose precision at every link but never a store. Below, the chain is drawn for n at pp0, the if (n < 2) of the factorial program.

The delivery

From Isabelle to your browser tab

The analyzer you run in the browser is not a reimplementation. Isabelle exports the proved definitions as OCaml, the OCaml is compiled to WebAssembly, and a background worker started by the playground calls it.

The model

Voblint and Goblint, side by side

Voblint follows the architecture of Goblint, a static analyzer for real C programs, and simplifies wherever a proof would otherwise have to model all of C. The project's own register of differences says what the claim is: “a simplified, machine-checked semantic model of Goblint's interprocedural context-sensitive architecture”, and not the exact implementation. Its vocabulary of locals, globals and side effects, and many of this page's examples, follow the FM 2026 tutorial on mixed flow-sensitivity by Goblint's authors.

The fine print

What Voblint can't do, and why proving is hard

A proof is only as wide as its statement. Voblint's guarantee is strong inside a small language and a precise set of assumptions, and this section is about the edges.

A small island in a large language

Goblint analyzes C. Voblint analyzes VIMP, a language small enough that its semantics could be written down and every analysis step proved against it. Hover a region to see what it would take.

What the theorems don't promise

That a run finishes

Every guarantee assumes the solve terminates. Proving that in general is out of scope; for intervals, the join-based rules can indeed run forever, and entry-state contexts can under any rule.

Precision

There is no completeness claim. A correct result may still say UNKNOWN for a check that holds.

A counterexample

REFUTED says the check fails in every run that reaches it, not that any run does. An error diagnostic likewise does not prove the point is reachable.

The code around the proof

The parser is generated from one grammar and tested. Isabelle's code generator, the OCaml compiler, wasm and your browser are trusted. Source positions, badges and graph drawings (OCaml rendering, this page) are unverified.

Two-way compiler equivalence

The compiler is proved correct in one direction, a forward simulation: every source run is matched in the graph. Soundness needs that direction only, and the backward direction is not proved.

Anything about Goblint's code

Voblint models Goblint's design. No theorem here speaks about Goblint's OCaml implementation.

Speed

The generated OCaml is slow. Its code is purely functional and written for easy proofs, mostly over association lists, with red-black trees only in a few places.

Facts like x != 5

Goblint's exclusion sets are absent. Over unbounded integers, joining 5 and 7 has no least exclusion set, so they cannot form a lattice.

Why this takes so long to prove

The analyzer that runs is the visible tip. Most of the work is underneath: definitions of what a program means, and proofs that every step respects them.

The formalization in cross-section

The iceberg counts volume; this counts structure. Every Isabelle session is a rock layer lying just above the highest session it builds on, from the logic at the bottom to the examples at the surface.
