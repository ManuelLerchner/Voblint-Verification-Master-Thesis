Static analysis you can trust, and why

Manuel Lerchner Master's thesis, Technical University of Munich Supervised by Alexandra Graß and Helmut Seidl About an hour to read, plus optional deep dives

A static analyzer reads your program and tells you something about every run of it, without running any. Once it says a check always holds, people stop looking at that line. So what happens when the analyzer itself is wrong?

Voblint is an analyzer where that question has a precise answer. Its soundness is proved in Isabelle/HOL, from the meaning of the source program down to the verdicts it computes, for every program on which its solver finishes, and the analyzer in the playground runs the code Isabelle generated from those same definitions. This page explains how it works, from what it tells you to what the proofs do and do not cover.

The output

What does it tell you?

Take the program below. It sets k to 10 and divides 100 by it, then divides 100 by an arbitrary 32-bit integer d, and finally asks whether q is positive. It also has a branch that no run can enter. Voblint analyzes it without running it. It checks every division and remainder for a zero divisor, and every signed operation and narrowing conversion for overflow, on its own, without being asked. Any other condition you want checked, you write as a __voblint_check.

The stakes

What if the analyzer is wrong?

Analyzers are programs, and programs have bugs. Many of them make the analyzer too cautious: it answers UNKNOWN where it could have said more. That costs precision, but the answer is still right. The dangerous bugs go the other way, when the analyzer says PROVED for a check that real runs violate, or DEAD for code that does run, and nobody looks at that line again.

Goblint, a mature analyzer for C, files these bugs under their own label. Below is one of them, reported in issue #1156 and fixed by pull request #1161, replayed with the verdict it got wrong. The notes in the margins are the analyzer's state at each line; the next two sections explain them, and the one after says what a machine-checked proof rules out.

The rest of the page builds toward one argument. At every program point, the stores real runs can have there lie inside the set of stores the analyzer's answer stands for. The proof chain states this as a chain of set inclusions, from source executions down to the verdicts, and each section before it explains one piece the chain needs.

The idea

What is abstract interpretation?

A test runs a program on a few inputs and watches what happens. It says nothing about the inputs nobody tried. Abstract interpretation takes the opposite route: it never runs the program, and computes with descriptions of values instead, such as “an integer between 0 and 5”. At every program point it keeps a description large enough to include every value a real run could have there, and it repeats the computation until the descriptions stop changing. If every value a description allows satisfies a check, then every run does.

Concrete runs and one interval per node

The figure applies this to a real program. Its first if keeps n between −4 and 4, so 3 * n cannot overflow and x takes exactly nine values. The figure draws the program's control-flow graph from the branch on x on: one node per program point and one edge per step. Each run appears as a dot at every node it reaches, placed at the value x has there. The abstract view replaces the dots with the one interval the analysis keeps per node. Soundness means that no interval leaves out a dot.

The intervals are not exact, though. The runs only ever reach multiples of three, and an interval cannot express that, so every band also covers integers no run has. On the left this makes a node look reachable although no run reaches it. On the right the guard rules out every value in the interval, and the analysis marks the check DEAD.

Each check gets one of four verdicts, and each states what the analysis established. PROVED: the check holds in every run that reaches it. REFUTED: it fails in every run that reaches it. DEAD: no run reaches it. UNKNOWN: the intervals are too coarse to decide. A check that no run reaches can still come out UNKNOWN, as pp7 does here, because DEAD means the analysis proved the point unreachable, not merely that it happens to be.

The vocabulary

What an abstract value stands for

Every abstract value names a set of concrete integers, its concretization γ. [−2, 5] names eight of them, even names infinitely many, ⊤ names all of them. Soundness is a statement about those sets: the set the analyzer gives a program point must contain every value a real run has there.

The analyzer computes with these abstract values instead of with single integers; it never handles the sets themselves, only their descriptions. Where one run holds x = 7 and executes x = x + 1, the analyzer holds the interval [0, 9] for x and computes [1, 10]. This single step of interval arithmetic covers every run in which x lies between 0 and 9.

Computing with descriptions costs precision. A domain can name only some sets, so the answer is usually wider than the exact set of values. That exact set may not be nameable at all, and even when it is, the analyzer may not find it. A different domain would not avoid this. For general programs, many semantic questions we would like to decide exactly are undecidable, so a sound analyzer that always terminates has to lose information somewhere. The rest of this page asks whether a wide answer still settles the questions you care about.

The five numeric domains

Sign

Seven values from “nothing” to “anything”. Joining 0 and >0 gives ≥0.

Interval

A lower and an upper bound, inside the range of the variable's kind (the axis shows i32). Among the four base domains, the only one that needs real widening, which stops at the kind's bounds; Int inherits it through this component.

Parity

Even, odd, or either. Joining even and odd loses everything.

Congruence

A remainder c modulo m. Modulus 0 means exactly the value c.

Int

Interval and Congruence at once, as in Goblint's integer tuple restricted to those two. The components sharpen one another after every arithmetic operation and every guard, so together they can decide a check that neither decides alone.

Reduction inside the Int product

An Int value describes the integers that both of its components allow. Each component on its own can miss what the other knows, so the product lets them sharpen one another. A sharpening step never drops an integer the value describes. It finds a smaller description, and a smaller description can decide a check that the larger one could not.

another precision example: a bound that looks wrong

A bound that looks wrong

Take an unconstrained n, set x = 6n + 5, and ask for x % 6. You would expect 5, but Voblint reports the interval [−5, 5] and decides none of the three checks. Is this an error in Voblint?

Combining two analyses through queries

Int combines two numeric domains, Interval and Congruence, inside one value. Separate analyses can also exchange information while the fixpoint is being computed. In the first program below, both guards hold at the assignment, so x = y and z is 1. Interval keeps one range per variable, and after the guards both x and y still span every i32 value. The order analysis keeps a set of pairs, each meaning that one variable is at most another. It knows x = y, but it tracks no value for z. Neither can prove the check alone. Run together, Interval's assignment asks all active analyses what x == y evaluates to, and the order analysis answers 1.

how the framework represents this

Each analysis supplies a local_spec: its transfers, which may ask questions, and a handler that answers questions from its own state. An answer to “what does e evaluate to?” is sound at a store if the value of e there lies in the answer. Two laws make answers combine. The top answer holds everywhere, so an analysis that cannot answer says ⊤ and claims nothing. Two answers that both hold can be met, so a question asked of all analyses gets the meet of their answers (mcp_answer).

The questions travel through a channel built from the state before the edge (ls_channel). A question asked again while it is being answered gets ⊤, as in Goblint's MCP.query', and a depth bound (query_depth) stops the recursion: the generated program aborts there, while in the logic the aborted branch answers ⊤. No analysis has to be ordered before another. ls_channel_sound proves the channel's answers hold.

An analysis proves its own laws once, as sound_local_spec, and the laws mention no other analysis. dg_spec_of turns a local specification into the record the equations consume, and dg_spec_of_contract carries the laws to the analysis contract. mcp_comp_sound gives that contract for every nonempty selection of distinct analyses, so the rest of the pipeline treats a combination like a single analysis.

The foundation

A trace, and why it follows one activation

To say that an answer covers every run, we first need a precise object that a run is. The soundness theorems on this page are statements about traces. A trace is the record a single run leaves behind: the nodes control passed through, and the store at each of them. A trace records one concrete run. It approximates nothing and quantifies over nothing.

If you have stepped through a program in a debugger, you have watched one being made. Every press of step moves control one node on and leaves the store at whatever the last statement made of it; the line the debugger highlights and the variables panel beside it are one (node, store) pair. A trace is that whole sequence, recorded instead of watched. The one panel a plain sequence throws away is the call stack, and the proofs need that panel.

For a program that is one long sequence of statements, a list of (node, store) pairs tells the whole story, and the run below would be exactly that list. Procedures make it insufficient.

sum(2) calls dec once and then calls itself, and the second activation does the same, so the run visits three activations of sum and two of dec. All of them walk the same single copy of the graph. Written as one flat list, the run therefore contains the same node again and again, and nothing in the list says which activation each occurrence belonged to.

What an activation trace is

Voblint uses the second shape below. An activation trace is one activation's view of the run. It holds one path, the activation's own, in execution order, and no step of any other activation appears on it. The activations around it are kept beside the path, and they are activation traces themselves: the caller that started this activation, stopped at its call node, and one trace for each callee that has already returned into it. The definition is recursive, just as calls are.

The shape is borrowed from the local traces of Schwarz et al. Those belong to a semantics of multithreaded programs, where the operations of different threads are only partially ordered. A sequential run has no such concurrency, so Voblint does not reuse the name.

The debugger has a name for that cut. Press step into at every call and you get the flat list: the callee's lines scroll past in the same stream as your own. Press step over instead and you get one activation's path, exactly as an activation trace records it. The callee still runs and its effect is still in the store when you land, but none of its steps appear on your line. The coloured bars in the figure above are the points where you pressed step over, and the box beneath each bar is the run you stepped over, which the trace keeps.

The interface

What you can ask a trace

A soundness statement asks a run only a few things: which node it has reached and what memory holds there, the store it started with, and who called it. Six observers answer these questions, each a few lines of definition on top of the trace datatype, and the soundness statements read a run only through them. The most used pair is sink_node and sink_store, the node and the store at the end of an activation's path.

in Isabelle: the datatype and its six observers

Start from the type. It is three lines long, and once activation_path is named, it reads like the description above: an activation trace is one path plus the activations around it. It is generic in the variables 'v, which core VIMP instantiates with its identities, var_id.

type_synonym 'v activation_path = "(cfg_node × ('v ⇒ int)) list"

datatype 'v activation_trace =
    Root                                                                    'v activation_path
  | Call   (activation_trace_caller: 'v activation_trace)                  'v activation_path
  | Resume (activation_trace_current: 'v activation_trace)
           (activation_trace_callee: 'v activation_trace)                  'v activation_path

There is one constructor per situation an activation can be in. Root is main, which nobody called, so it carries a path and nothing else. Call is an activation that is running and will return to its caller, activation_trace_caller, which it holds. Resume is the same activation after a callee has returned. activation_trace_current is the activation stopped at its call node, and activation_trace_callee is the finished callee. The callee is kept whole instead of being spliced into the path, so a returned call remains one box you can ask questions about.

The nesting simplifies the question every soundness proof has to ask: “Which runs can be standing at node v, and what does memory hold there?” With activation traces, the answer is the end of one path. With the flat list, you would have to scan an interleaved sequence and decide, for every occurrence of v, whether it belongs to the activation you are reasoning about. The analysis answers per program point, and per point and context once a policy keeps copies of a procedure apart. Activation traces are shaped so that this per-point question can be read off directly instead of being reconstructed.

Grouping by activation instead of by procedure has one more consequence. In this run, sum is one procedure with three activations, and the trace keeps all three apart because each is its own box. The analysis cannot keep every activation apart. It has to decide in advance how many copies of sum to reason about separately, and a context is the result of that decision. Because the concrete side distinguishes every activation, the proofs can check that whatever the abstract side merges is still covered.

The analyzer never builds a trace

It could not usefully do so. Every trace is finite, but nothing bounds its length or how deeply it nests: a recursion has one activation per level, and as soon as the program reads an unconstrained input, the set of all traces is infinite.

An activation trace exists only as a value in the logic. It gives soundness something to be a statement about, and the proofs quantify over the set of traces without anything ever enumerating it. The generated code confirms this: of the — lines of OCaml exported from these theories, none mentions activation_trace, valid_activation_trace, sink_store, caller_of or node_collect. The specification is not part of the analyzer.

The values

What a VIMP integer is

Before saying what a run does, we have to say what it computes with. Take this program, which Isabelle also evaluates through the analyzer (overflow_verdicts):

fun main() {
  i32 x = 2147483647;
  x = x + 1;
  __voblint_check(x < 0);
}

Over mathematical integers x ends at 2147483648 and the check is false. In C on a 32-bit int the addition overflows, which the standard leaves undefined. VIMP gives the program one meaning: x is declared i32, so x + 1 wraps to −2147483648. The check holds in the only run there is.

Run it with --analysis interval, and two things come back. The arithmetic table reports ERROR signed integer overflow in + at x + 1. The check comes back UNKNOWN, because Interval by default treats a possible signed overflow as Goblint does under its default sem.int.signed_overflow = assume_top: the result may be any i32. With --signed-overflow assume_wraparound, Interval wraps as the semantics does, keeps x = [−2147483648, −2147483648] and the check is PROVED. The ERROR is the same under both settings, because the option changes how precisely an analysis bounds a wrapped value, not what the program computes.

Each answer means what the first section said. The ERROR is a refuted obligation: every store that reaches x + 1 makes the mathematical sum leave the i32 range (run_voblint_arithmetic_refuted). That is a definite overflow only for a run that gets there, and the theorem does not say one does. A point the arithmetic table does not name is safe: no reaching store divides by zero, overflows a signed +, -, * or /, has a signed % whose quotient leaves its kind, or converts a value its target kind cannot hold (run_voblint_SAFE). PROVED is about the wrapped value: the check holds in every run that reaches it, with x + 1 computed as the semantics computes it. Run the assume_top version ↗ Run the wraparound version ↗

Kinds, and where wraparound happens

A kind is one of eight machine integer types, i8, u8, i16, u16, i32, u32, i64 and u64 (ikind). Each has a range, and ik_norm maps any integer into it by keeping the low bits, two's complement for a signed kind. Values stay HOL integers; the kind only says which of them a variable may hold. A program declares the kind of every variable in C style, u8 x;, global i16 g;, fun u32 f(i8 n), and the parser rejects a name that no declaration introduces.

Wraparound happens at the operation, and the operation has a kind of its own. As in C, both operands are first brought to a common kind by the usual arithmetic conversions: a u8 plus an i32 is computed at i32. In u8 x = 250; x = x + 10; the sum is 260 at i32, and storing it back into the u8 wraps it to 4.

A variable is an identity, not a name

Two procedures may both have a formal n, one i8 and one u32. A kind table indexed by names could not hold both. The semantics therefore stores values under identities (var_id): GlobalId x for a global, ScopedId f x for a local or formal of f, ReturnId f for the kind f returns, and ReturnVar for the slot a return writes and a caller reads. Whether a variable is global is now read off its constructor, so the semantics needs no separate list of globals.

C also lets an inner block redeclare a name: { i8 x = 7; … } inside a procedure whose x is i32. The parser resolves this before the program reaches Isabelle. It renames each shadowing declaration to a fresh name, x#2, x#3, …, that no source program can write, so every declaration in a procedure has its own ScopedId and its own kind.

From surface VIMP to core VIMP

What you write, and what the parser builds, is surface VIMP: it writes x + 1 and leaves conversions implicit. What the semantics executes is core VIMP, which writes every kind and every conversion down. The step between them is the elaboration, and surface VIMP has no semantics of its own: a surface program means whatever its elaboration does in core VIMP. Core VIMP's expressions (exp) are literals TN, variable reads TVar, arithmetic TArith and conversions TCast, each carrying its kind, plus comparisons and the logical operators, which yield 0 or 1. elaborate translates a surface expression (src_exp) at the kind its context wants, inserting the conversions C would perform; elab_com does the same for statements (src_com) and resolves each name to its identity. In main above, x = x + 1 becomes

Assign (ScopedId main x)
  (TArith I32 AAdd (TVar I32 (ScopedId main x)) (TN I32 1))

and the u8 version becomes TCast U8 (TArith I32 AAdd (TCast I32 (TVar U8 x)) (TN I32 10)). eval evaluates such a term with no kind table: it wraps at every TArith and TCast with the kind written on the node. The elaboration is an Isabelle function, and its output is well-typed (wt_com_elab_com), so every value an expression produces lies in its kind (eval_in_range).

The remaining conversions happen where a value is written. An assignment, a call's argument and a call's result are converted to the kind of the identity that receives them (kind_conv), and a return converts its value to the procedure's return kind. A call narrow(200) to fun i32 narrow(i8 n) enters with n = −56. As a consequence no store the graph's activation traces reach holds a value outside a variable's kind (node_collect_in_kinds), and the analyses' soundness proofs use this fact.

What the theorems quantify over

There is one operational semantics, pstep, written once over an evaluator, a test for globals, a return slot and a conversion. Core VIMP's step pstep is that semantics instantiated with eval, GlobalId as the globals, ReturnVar as the slot and kind_conv. The analyzer receives the parsed program p and its kind declarations ds, and the soundness theorems are about the runs of the elaborated program elab_ptable p ds under pstep. A run starts from any store in init_stores: every global is 0, and every other identity holds some value of its kind. A local declared without an initializer is reset to an arbitrary value of its kind each time its declaration runs (pstep_declare). The graph, the activation traces and the collecting semantics in the next sections are generic in the same way, and the analyzer's theorems use their core-VIMP instances.

Three questions about these guarantees have different answers. The analyzer's soundness for runs of core VIMP is proved: the theorems quantify over exactly those runs. What a surface program means is fixed by definitions, and the elaboration is one of them, defined in Isabelle and applied inside run_voblint; that these definitions say what they should is argued below, not proved. The OCaml parser, and whether VIMP's integers behave like C's, are trusted.

The proof stops at the parser. Isabelle receives p and ds after block scopes have been resolved into fresh names and declarations into those reset calls. That this follows C's scoping, and that every use of a local comes after its declaration, is trusted: the parser checks it and rejects a program that breaks it, and no theorem covers it. The same holds for the source line printed next to an arithmetic diagnostic. The theorem names the graph node, and the CLI finds the line through positions the parser recorded.

Whether these definitions are the integers you meant is not a theorem either. The meaning of a surface program is fixed by several definitions read together: ik_norm, the usual arithmetic conversions, elaborate and elab_com, eval, kind_conv, the declaration rule and pstep. Two of them differ from C on purpose. Signed overflow wraps, as with -fwrapv, where C leaves it undefined; the arithmetic diagnostics are how you learn that a program may depend on it. Division by zero is defined, a / 0 = 0 and a % 0 = a, and is reported the same way.

The meaning

What a run is

A semantics is a rule for what a program does: given a state, which states may come next. Writing it down turns “what the program really does” from an appeal to intuition into a set you can quantify over.

Voblint relates two small-step semantics to a third, trace-based description of executions, because the three objects it has to relate have different shapes. A source step (pstep) rewrites a program that is still program text, carrying the store and a stack of caller frames. A CFG step (cstep) moves a position through a control-flow graph, carrying a stack of return points. The third does not take steps. activation_trace is the activation trace from the previous section, and valid_activation_trace is a rule that says which of those values the graph admits. It judges one activation with its whole history at once, instead of moving from one state to the next.

Soundness is stated against the third, because of what the analysis answers. It gives one value per program point, so the soundness claim has the form “at node v, this value covers every store a run can hold there”. pstep has no notion of a node, so the claim cannot even be stated against it. cstep has nodes, but its state is a whole configuration including the call stack, and while it holds the current activation's store, it does not record which activation that is, so contexts, which are read off the activation, cannot be stated against it. Activation traces can: the traces whose path ends at v are exactly the activations standing there, one box each, and each holds the store at the end of its path.

The semantics differ in the three stacks below the figure. At an open call, the source keeps a Frame: the caller's store and the variable to assign. The graph keeps the same and the node to return to. An activation trace keeps the caller itself, whole, as a field. Soundness has to name a program point, say which stores can be there, and do so one activation at a time, so the table asks all three the same four questions. The table adds a fourth candidate: activation_path is a list of pairs, and one such list for the whole run, instead of one per activation, is the flat list from the trace section.

The repeated answers follow from what the stacks keep. A configuration is a snapshot, so there is no path to read off it. The frames hold the callers' stores, so an activation's own entered store is lost as soon as it assigns a variable. A frame names a return point, not a run. The flat list has all the steps but not the grouping, so every answer requires a scan.

The last row is the reason the proofs use activation traces. When a call returns, the proof has to say that this callee returned into that caller. With the caller inside the value, the return rule simply states caller_of callee = Some caller. Against a stack there is no term for the caller's run that a rule could refer to, and this matters for recursion. Contexts later read the same two fields: caller_of for the activation that made the call, and entry_store for the store it was entered with.

The choice follows a general rule. A soundness claim can only distinguish what the semantics it quantifies over distinguishes. An analyzer that keeps activations apart therefore needs a semantics that keeps them apart, or its theorem cannot say what it covers. Choosing the finer semantics as the base loses nothing, because the coarser views are projections of it: node_collect drops the activation, and activation_collect keeps its context. A coarser base, in contrast, cannot be refined afterwards.

From one run to one answer per node

The figure above follows a single run, but the analyzer never looks at runs. What it produces is a table keyed by program point, with nothing in it about paths, calls or activations (contexts split the keys further, as the section on procedures shows). To compare the two, we bring the concrete side into the same shape. Take every activation trace the graph admits, which is the set valid_activation_trace builds up by starting at the entry node, following an edge, entering a call and returning from one. For each trace, note the node where it ends and the store it ends with.

The theories write this with a little notation. g is the compiled graph, S the set of stores a run may start in, and 𝒢 the classifier that says which variables are declared globals. 𝒯𝒢,g,S is the set of valid activation traces of g starting from S (valid_activation_trace). For a trace t, sink_node t and sink_store t are the node and the store at the end of its path. The stores collected at a node v, 𝒞𝒢,g,S v (node_collect), are then:

𝒞𝒢,g,S v =
  {sink_store t | t. t ∈ 𝒯𝒢,g,S ∧ sink_node t = v}

The result is one set per node, holding the stores a real run can have there. Neither of the other two semantics yields this directly. Over pstep there is no node v to index by. Over cstep it can be written, but the only finer index available there is the call stack, not the activation.

This is also where the grouping by activation is given up on purpose. A trace has to belong to one activation for “ends at v” to mean anything; the collection then forgets the activation and puts all stores at v into one set. activation_collect is the variant that keeps a key per activation, and a context decides how much of that key to keep.

Soundness asks only for containment, not equality: the answer at v has to cover the set beside it, and may cover much more.

Here it covers much more. Runs only ever reach pp2 with n equal to 2, 1 or 0, but the answer admits every i32. Three things caused this, and the first two get their own sections later. First, the three activations of sum were merged into a single entry before anything was computed. Second, the lower bound of that merged entry kept moving down, so the solver stopped following it and jumped to the smallest i32. Third, at that bound x - 1 in dec may overflow, and Interval then answers the whole kind, so the upper bound is lost as well; the arithmetic table warns about that possible overflow. As a result, the check at pp10 comes back UNKNOWN, on a program in which every run makes it true. The rest of the page is about this gap: how a sound answer is computed at all, and what it costs to make it narrower.

The computation

From a graph to equations to values

The compiler turns a program into a control-flow graph, and the analysis turns that graph into equations. In this single-procedure example, there is one unknown per node and one term per incoming edge, and each term applies that edge's action to the value at the edge's source. With procedures, unknowns will be keyed by node and context. Starting from the requested result, the solver computes values for the unknowns that result depends on. To the rest of the pipeline the solver is a black box: equations and a query go in, and one abstract value per unknown it reached comes out.

How the compiler builds the graph

The compiler reads a procedure one statement at a time and turns each statement into a numbered node with outgoing edges. Each statement is compiled with the number of the statement that follows it, so its target is known before it is compiled. The figure replays this on the counting loop, with the node numbers and edge labels the real compiler produces.

Inside the solver, a right-hand side is a strategy tree: a small program that reads other unknowns one at a time, may publish values to global unknowns along the way, and ends in an answer. Because each read hands the rest of the tree a value, the solver can evaluate an equation step by step and follow only the dependencies the current question needs. The details below show the tree type and how the generator builds one tree per node.

how an equation is represented: strategy trees

What an equation is made of: strategy trees

One level down, the solver never sees ⊔ or assume. It sees each right-hand side as a strategy tree, which spells out every step of the evaluation: QueryL reads a local unknown, QueryG reads a global one, Side contributes a value to a global, and Answer returns the result. A query does not name its next step directly. It holds a function from the value it reads to the rest of the tree, so the solver learns which unknowns an equation depends on by evaluating it. Trees and the systems built from them are the vendored solver's own language: a whole equation system is one function from an unknown to its tree.

datatype ('x, 'g, 'd) strategy_tree =
    Answer 'd
  | QueryL 'x ('d ⇒ ('x, 'g, 'd) strategy_tree)
  | QueryG 'g ('d ⇒ ('x, 'g, 'd) strategy_tree)
  | Side 'g 'd (('x, 'g, 'd) strategy_tree)

Building such trees directly is awkward. Because a query holds the rest of the tree as a function, each read the generator emits has to be written inside the continuation of the previous one, so the nesting grows with every read and the last step ends up deepest. Voblint therefore generates each right-hand side as a strategy program: a tree that still lacks the continuation consuming its result, which makes it a function from that continuation to a tree. Two programs compose by passing the second to the first as its continuation, and do-notation writes exactly this composition, so the generator can state its reads in the order it performs them. sp_compile then closes the last continuation with Answer, which yields a tree.

The two are easy to confuse, so from here on the notation tells you which one is shown: a program is written in do-notation, a tree with its constructors. Everything the generator builds is a program, and the names say so (dg_spec_edge_program, fold_rhs_program); sp_compile is the one step that turns a program into a tree.

Only the dashed stage is Voblint's own, and it is finished before the solver runs. The solver receives an ordinary tree, so the vendored correctness proof applies unchanged.

The generator works one edge at a time, then one node at a time. dg_spec_edge_program turns a single CFG edge into a small program: read the unknown at the edge's source, apply the edge's transfer, answer. A node with several incoming edges gets one such program per edge, and fold_rhs_program folds that list into one program that joins their answers; this is where the ⊔ of a join node goes. Compiling the program gives the node's tree.

Writes to globals are buffered (routed_node_rhs_buffered). The buffer collects the writes per key and emits each key once per flush, as a single Side with the collected contribution. At a node into which at most one call returns, it emits before the node's next read of a local unknown, so a call publishes its seed before it asks for the callee's result. At a node where several calls return, it emits at the end, after the last read. A write of bot is dropped (flush_sides): joining bot into a global changes nothing, but publishing it would still cost the solver an update and a destabilization of that global's readers. Doing this for every node builds the equation system eqsT, one tree per unknown. The figure below steps through it for the loop head.

Compiling every node of the counting loop, not only the four shown, gives its eqsT, and this one function is the entire equation system the solver receives. Every equation is now a chain of reads ending in an answer. The ⊔ and the assume shown in the equations above are no longer visible at the top level. They sit inside the answer, as arithmetic on a domain the solver knows nothing about.

What the solver is given

eqs E H B X

The TD solver is demand-driven. It is asked for one unknown and evaluates that unknown's tree, and every QueryL on the way asks for another unknown, recursively. It computes exactly what the first question turns out to need. Voblint always asks the same question: the exit of the entry procedure under the root context.

root_query p = (cfg_exit (prog_cfg p), root_ctx)

A terminating run ends at that point, so asking for it pulls in, one query at a time, every point its value depends on. The vendored solver therefore promises a partial post-solution with three properties. It covers the question. Its covered set is closed under the dependencies the trees take. And for every covered unknown, the tree's answer is below σ's value there, with its contributions below σ at the globals they write. Read as a pair, the answer together with the partial map of its contributions, that last property is the usual condition on a side-effecting right-hand side (part_post_solution_iff_rhs_pair). The middle property speaks only of direct dependencies; part_post_solution_implies_trans_dep_subsumed extends it to all of them, so everything transitively reachable from the question lies inside the covered set.

Every node a run can reach has a path in the graph to its procedure's exit, so the solver's backward queries reach it (live_unknowns_cover). A key outside the solved set is still defined to read as bot:

solved_local_reader vars σ k =
  (case k of Inl vc ⇒ (if vc ∈ vars then locals (σ (Inl vc)) else bot)
           | Inr _ ⇒ bot)

This is sound because no run reaches such a key, and the empty set of stores covers every run that does (solved_local_reader_uncovered). Code inside a reached procedure that the analysis proves unreachable is different. It is solved, to bot, and that is how a DEAD verdict arises.

What comes back

the black box: widening, and the solver step by step

Why a loop needs widening

A loop can run any number of times, so following it pass by pass may never end. The analysis instead widens: when a bound keeps moving, it jumps straight to the limit of the variable's kind, 2³¹−1 for an upper bound of an i32. This is safe, and for intervals it stops the climb. The analysis then narrows, using the loop's own guard to pull the bound back. Warrowing combines the two: it widens while a value grows and narrows once it shrinks.

Nothing in the equations marks a loop head. The solver finds the widening points itself, whenever it meets an unknown that is already being computed, and it warrows every local unknown at such a point, whichever rule a run uses for the globals. A domain takes part through executable_domain, which includes the solver's warrowing class. Step through it below.

Replaying the real solver. The playground can record the generated analyzer's solver trace and replay it on the graph: each query and its answer, each value stored, each side effect into a seed, each update and the readers it destabilizes, and the context each call is routed to. The trace is an unverified observation of the verified computation, not part of any theorem. The section on watching the solver says how it is recorded.

Procedures

How many copies of a procedure to keep apart

A procedure can be analysed once for all its callers, or separately for different calling situations, and that choice trades precision for cost. Everything so far had one procedure, and a call breaks two assumptions at once. The callee's entry state now arrives from somewhere else in the equation system, and several call sites can reach the same copy of the callee. The solver's side effects handle both, and two settings tune them. The first decides how many separate copies of a procedure the analysis keeps apart. The second decides how the values that several call sites send into one copy are combined. This section covers the first; the second follows once the system those copies live in is clear. Both settings affect precision and whether a run finishes, never soundness.

Side effects: writing an unknown you do not own

Every right-hand side so far only read. It queried other unknowns and answered with a value for its own, which is why the walkthrough above could be drawn as one variable changing. The solver allows one more operation. A right-hand side can publish a value into an unknown it does not own: the solver joins the value in, records who published it, and re-evaluates every right-hand side that had read that unknown. In a strategy tree this is a Side node, the part the walkthrough left out.

Voblint publishes for exactly two reasons. The first is a flow-insensitive program global: each one has its own unknown, which only the edges that assign it publish to and only the points that mention it read. The second is a call. A caller does not write the callee's entry point directly. It publishes the entry state under a key (Activation_Seed), which the callee's entry reads back. The vendored solver can only side-effect global unknowns, so this key is a global stand-in for the local unknown that Goblint writes with sidel. This is a recorded difference from Goblint, made on purpose.

Both settings act on this one publication. Contexts decide which key a call publishes under, and therefore how many copies of a procedure exist. Globals decides how several publications to the same key are merged.

What a call adds to one procedure's equations

An analysis does not hard-code what a call does. Three pieces decide it. enter builds the callee's entry state from the caller's state. A context policy picks which copy of the callee receives that state. combine merges the callee's exit state back into the caller. enter and combine come from the analysis; the policy is a run setting. The framework wires all three into equations in the same way for every domain, and each connection carries its own soundness obligation.

This wiring stays within one procedure. Each node gets one equation, built from that node's incoming edges, and a call site is simply a node whose contribution publishes and queries. Generating the equations never looks into the callee, which is why a recursive call needs no special case: the generator does not follow the recursion, and how deep it goes is a question for the solver. A real run does go into f, and the step-through of a run follows one through a program with calls.

Context sensitivity: how many copies of a procedure

The equations above simplified one thing. Their unknowns were bare program points, so any two calls to f would land in the same copy of it, and the entry states they produce would be merged. An analysis can be set up to keep those call sites apart. A context is the key a procedure is analyzed under: call sites that produce the same key share one copy of f, and call sites that produce different keys each get their own. This setting picks how that key is computed, and there are several strategies.

c is main's own context. c₁ and c₂ are the keys the strategy returned at the two call sites, and each appears in exactly two places: the key the call publishes under, and the exit it queries. The rest of the equation stays as before.

How the strategy changes precision

Three strategies ship, and they differ only in what they use as the key. The call string also takes a depth, so the figure below compares four settings. It concerns a small program in which wrap passes its argument straight to scale, which doubles it, so a is 2 and b is 8.

The equation system

How the solver explores an implicit equation system

Every figure so far showed a handful of equations, as if the system were a list someone wrote out. The generator is a total function from a program point and a context to a right-hand side, defined on the whole type of nodes and contexts, so there is no finite table of equations to hand over. A fixed program has only finitely many nodes that matter, but the contexts its calls create need not be finite. A run produces only the part that its query reached.

the whole system for a five-procedure program

A program point is a cfg_node: a numbered statement, or a procedure's entry or result, named by an arbitrary string. A context is whatever the policy keys copies by. That is a call_string, a list of call sites, or, under entry states, the list of abstract values the call binds to the callee's formals, read off the entered tst. Neither type is finite, and compiled_routed_eqs_for gives an equation for every pair of them. No step builds the equations, no table is allocated and no enumeration needs a bound. A solve evaluates the part of the system its query reaches.

Five procedures are enough for a picture like the one below. The arrows trace exactly the program's call graph: main calls w and f, f calls itself twice and calls g, and g calls h. w calls itself with a value nothing constrains, so the analysis cannot tell its copies apart and keeps one.

The source does not say how many copies of each procedure the analysis will keep, or which keys they get. The context policy decides that, so the filled cells below only take shape during a run.

Nothing builds this system. An equation system is an eqsT, and eqsT is a function type, 'x ⇒ strategy_tree, from an unknown to its right-hand side. compiled_routed_eqs_for defines one such function, and a function in Isabelle/HOL is total: it has a value at every argument of its type. So the right-hand side for every pair of a program point and a context is already defined. Nobody constructs it. The solver evaluates it when it needs it, so the infinite size of the system has no run-time cost.

Only a query produces something finite. The solver receives the system and one unknown, and returns a partial post-solution (part_post_solution): every unknown it stabilised is at least what that unknown's equation computes, over the set of keys it reached. That set is finite because the run terminated; the system itself is infinite.

A key the solver never touched reads as bottom. The theorem shows that this loses nothing: the solved keys contain the root query and are closed under every step a run can take (live_unknowns_cover), so every key a run reaches is among them, and every answer in the result table is covered, including bottom at points no run reaches.

Shared state

When several callers share an entry

The two settings change different things in the same picture. Context sensitivity decides the columns: which unknowns exist, and how many copies of a procedure there are. This setting decides what a cell holds when several writers publish to the same key. It never adds or removes a key. It can therefore stop a value from growing forever, but it cannot stop the number of copies from growing.

Where the writes meet

In the playground this is the Globals setting. “Globals” there means the solver's global unknowns, not VIMP's global declarations. Under the default placement the two meet at one point: a program's globals are part of the state a call publishes, so they cross a call through a solver global. Under the other placement each program global has a solver global of its own, which the end of this section describes. This is the channel drawn as a dashed arrow in the previous section, where a call site writes the callee's entry key and the callee's entry equation reads it back. The rest of this section is about those entry keys, and this setting decides what happens when several writes reach one of them.

Three of the four programs the guide table further down measures, in one file. The fourth is a recursion whose argument never stops climbing, and it cannot sit beside them: whether that one finishes at all is the first thing this setting decides. Each call site is lettered, because a call site is what publishes to a key: A and B both write p's entry, C is g's only writer but publishes more than once, and D and E both write s's.

Every key here takes several contributions, so all five settings have something to do, and they do not agree. Warrow widens p's and g's entry away and loses both checks. Warrow per origin keeps those two and still proves s's check, over the wider range [−9, 9] and with a warning that 9 / (a + 2) may divide by zero. Bounded narrowing gives the same answer. Join and Join per origin keep all three, and neither of them finishes on a recursion whose argument climbs, which is why neither is the default. The four-program table further down is those runs.

Widening only helps where a key is shared. Run f(x) { f(x + 1); } from f(0) with --context none, and Warrow finishes: one key receives every contribution, and widening stops the climb at the largest i32. There x + 1 may overflow, so the answer it finishes with lets x be any i32, as the table below shows. Run the same program with entry-state contexts and no setting here finishes. Each new argument is a new context, hence a new key with a single writer, and none of these rules has anything to widen against. Limiting the number of copies is the job of the context setting.

Five rules for combining writes to one key

A site sends the state its call binds the callee's parameters to, so [0, 3] means one site says the parameter arrives somewhere in that range. The rule combines these contributions into a single value, the callee's entry state, from which the callee is analysed and seeds its own calls.

One site can send several times. A right-hand side is not run once; the solver re-evaluates it whenever an unknown it reads has moved, and each re-evaluation publishes again at the same key from the same origin. Site C above does that each time the loop head's value moves, which is a few rounds however many turns the loop runs for. A contribution comes back smaller when narrowing has pulled a widened value down and the site is recomputed from it.

Below, A and B are two writers at one key. The numbers are not taken from the program. They are chosen so that A sends three times, first smaller and then larger, and this sequence tells the first four rules apart: step 2 separates Warrow from the rest, step 3 separates Join from Join per origin, and step 4 separates Join from Warrow per origin. Telling Bounded narrowing apart from Warrow per origin takes more steps. The values are intervals because the rules hold for any domain with a join, a widening and a narrowing, and Interval is the domain where widening does something the join does not. Sign and Parity are short enough lattices that their widening is defined as the join.

Why not always use Join?

Because the cost of joining grows with the length of the chain. A joining rule never widens, so a value that keeps growing is followed one step at a time, and the solver needs a round for each step; widening covers the same chain in one step. On f(x) { if (x < N) f(x + 1); }, started from f(0), every rule proves x <= N. But as N grows from 64 to 4096, the two joining rules go from 5 ms to about 240 ms, while the three widening rules stay at 4 ms. Without the bound, the growth never ends, which is the no answer in the table below.

Which Globals setting should you pick?

No setting is best everywhere. They trade how quickly a growing value is cut off against how much a merged value forgets. Nothing proves any of them terminates on every program: Voblint assumes termination per program, so a bad choice shows up as a run that never finishes, not as a wrong answer.

Start with Warrow

The playground's starting point. With widening, the analysis of a recursive call whose argument keeps growing still finishes. It cannot stop entry-state contexts from multiplying, though: those need context None or a call string.

UNKNOWN with several callers?

Try Warrow per origin. It widens each call site's contribution on its own, so one caller's growth is not blurred into a jump to the kind's bound for all of them. It is not always more precise: in the last row below it keeps a wider range than Warrow. Bounded narrowing widens per call site too, and bounds how long each one keeps narrowing.

Join and Join per origin on intervals

Precise when a procedure receives few values, but they never widen: a call chain that keeps growing an argument gives no answer within the time limit.

If a run does not finish

The playground has no timeout; the command-line analyzer takes one with --timeout. Press Cancel, or change any setting, then pick Warrow, Warrow per origin or Bounded narrowing, and switch entry-state contexts to None or a call string.

Recursion with a growing argument

Both settings meet in recursion. f(x) calls f(x + 1) forever, so real runs wind outward on an endless spiral: f(0), f(1), f(2), each turn wider than the last. The analysis has to describe every turn with finitely many contexts, and whether it can depends on the settings: Join and entry-state contexts follow the spiral and give no answer within the time limit, warrowing cuts across it. Cutting across it cannot prove x >= 0 here, because the check really fails once a run is deep enough for x + 1 to wrap. Switch to the same function stopped at x = 10 and every setting finishes and proves it.

Where program globals live

So far a VIMP global has behaved like a local that every procedure can see. It travels inside each point's state: into a callee with the caller's state, and back out through combine. The playground's Program globals setting (--program-globals on the command line, program_globals in the theories) offers a second placement, the one the FM 2026 tutorial calls flow-insensitive.

Under Flow-insensitive, each declared global gets a global unknown of its own, and the points stop carrying it. An edge that assigns g publishes the new value of g to that unknown, an edge whose expressions mention g reads it, and a call reads only the globals its arguments mention. A point that touches no global depends on none, and a write to g re-runs only the points that read g (read_g_depends_on_g_only and write_h_publishes_h_only check this on one reading and one writing edge). The initial value 0 is published by the program's entry like any other write.

This placement costs precision, because one value has to cover everything the global ever holds, at every point. Take set() writing Gx = 1 and get() returning Gx, called in that order from main. Flow-sensitively, Sign carries Gx = + from set's exit into get and proves 0 < y. Flow-insensitively, the unknown of Gx joins the initial 0 with the written 1, Sign can only say Gx ≥ 0, and 0 < y stays UNKNOWN. Run it flow-sensitively and flow-insensitively to compare.

So why offer it? For a sequential VIMP program it only loses precision, as it does here. The reason is the language VIMP could grow into. The FM 2026 tutorial names multi-threaded code as a main source of mixed flow-sensitivity: a thread-modular analysis collects the values threads exchange through shared globals flow-insensitively, so it can track each thread's own state flow-sensitively without considering every thread that may run beside it. Goblint analyzes concurrent C this way. VIMP has no threads, so here the setting shows something narrower: the framework and its end-to-end theorem already carry a mixed flow-sensitive analysis. An extension with threads would reuse this machinery and add a thread semantics and synchronization.

Both placements carry the same end-to-end theorem, run_voblint_source_sound, because the setting is an argument of the analysis function it is stated about. The flow-insensitive one comes from a lifter, keyed_split_spec, that wraps the active analyses. Its soundness proof (keyed_split_contract) rests on a fact about the concrete semantics: a step leaves every global it does not assign unchanged (edge_step_frame), so skipping the publication of an unwritten global loses nothing. Only per-variable state splits this way. The order analysis relates variables to each other and keeps its whole state at the points.

The global unknowns are side-effected, so the Globals setting above decides how their writes merge. Choosing Flow-insensitive switches it to Bounded narrowing unless you picked a rule yourself, because under plain warrowing a global's unknown that is widened and narrowed in turn need not settle.

The guarantee

What does “verified” mean?

The first section showed what a verdict promises a user. This one says where that guarantee starts and where it stops. The congruence bug at the start of this page is the kind of mistake a proof rules out. VIMP's % is c_mod, and the congruence domain has to prove that c_mod i j lies inside γ of whatever it answers. An operation that rounds the wrong way cannot satisfy that obligation. Voblint's analysis is written in Isabelle/HOL, and theorems there state that, once the solve finishes, its answer covers every store a real run can have. Isabelle checks every step of those proofs down to the axioms of its logic.

What came before, and what is new

Before the guarantee itself, it helps to know which parts of it Voblint builds on. Much of the machinery rests on prior work, some is adapted here, and the contribution is the formalization that connects it end to end with a machine-checked proof.

Correct with respect to what?

Every theorem here assumes one thing about your program: what a run of it does. For core VIMP that is pstep and what it runs on: eval, which wraps every operation into its kind with ik_norm, the conversion at every write, the initial stores, and operators down to c_mod taking its sign from the dividend, as C does. For the program you wrote, add the elaboration that turns it into core VIMP. Isabelle checks that the analyzer's answers cover every core run these definitions admit. It cannot check that they are the definitions you meant. Whether the meaning they give a surface program is what a C-like language does is a reading task no proof discharges; the section on VIMP's integers names the places where it deliberately is not.

The graph and activation-trace semantics are not on that list: they are reached from pstep by proof (source_reaches_node_collect).

What remains to be read lives in one session, Voblint_VIMP: syntax, kinds, identities, core expressions and commands, the elaboration, the generic step pstep and library calls, plus the theory VIMP_Semantics that puts them together: the initial stores and the three definitions kind_conv, pstep and elab_ptable. Everything else, from the compiler and the equation generator to the solver, the six analyses and the result table, Isabelle's kernel has already checked against them. This holds for PROVED, REFUTED and the reachability of checks (run_voblint_check_sound); a reviewer also reads the theorem statements themselves. The DEAD and arithmetic theorems are stated over the compiled graph's collecting semantics, so reading them at source level also takes the compiler and the graph semantics.

Where the proof starts and stops

A proof covers a precise statement about precise definitions. Whatever the statement does not mention is trusted: it has to be correct for the guarantee to reach you, but nothing here proves it.

Watching the solver work

The solver trace in the playground's run_voblint: call and answer panel, like voblint --trace --verbose on the command line, lists what the solver did: each unknown it solves, each query and the value it returns, each side effect into a seed, each update and the readers it destabilizes, and the context each call is routed to. The solver result is the exported computation of proved equations; its trace calls come from code equations proved equal to the untraced ones. The argument

The proof chain

Inside the boundary drawn in the previous section, soundness is a chain of set inclusions. At one program point, start from the stores real runs have there, and widen step by step: first to the stores the graph's activation traces reach, then to those traces split by context, then to what the solver's answer concretizes to. Each link is a theorem of its own. The analysis may lose precision at every link, but it may not lose a store. One last step turns the final set into the verdict you see. Below, the chain is drawn for n at pp0, the if (n < 2) of this program:

fun i32 f(i32 n) {
  if (n < 2) {
    return 1;
  }
  i32 r = f(n - 1);
  return n * r;
}

fun main() {
  i32 x = f(2);
}

main calls f(2), which calls f(1), so two runs reach pp0: one with n = 2 and one with n = 1.

The five facts the chain rests on

The chain connects real runs to the verdicts, and five facts support it: two theorems and three obligations the analyzer has to discharge. Remove one to see which answers stop being covered.

What the proof forced us to make explicit

Some obligations look like proof bookkeeping, but several of them correspond to design constraints that only became visible once the soundness theorem had to be stated precisely. The first two below are necessity results: weakening the condition while keeping the others admits an unsound claim. They show that these conditions are needed, not that every premise of the development is. The third is another constraint the proof exposed; the executable witness that the equation system obeys it awaits a port to the current analyzer.

more constraints the formalization made explicit
  • An analyzer that decides nothing is sound. An analyzer that answers UNKNOWN at every check satisfies the soundness statement (unknown_everywhere_sound), while one that answers PROVED everywhere violates it (proved_everywhere_unsound). This is why the theorems come with non-vacuity witnesses: evaluated verdicts that are actually decided (nv_check_proved_sound).
  • A domain obligation rules out the Goblint bug for every operand. Any abstract remainder that returns the constant 1 for the class 1+2ℤ modulo 2 violates the statement that the shipped congruence remainder satisfies, at −5 (prefix_congruence_mod_unsound). Goblint's regression test samples one program; the obligation covers all of them. This is machine-checked; the upstream behaviour is documented, not re-run here.
  • Entry states must be covered in pairs. When enter returns several alternatives, each pair of caller continuation and callee entry has to cover the run together. Covering the caller store with one pair and the entered store with another lets the combined result exclude the run's real value (unpaired_entry_cover_unsound).
  • Publish to a global unknown only complete contributions. The solver's update rules record one contribution per origin, so the equations buffer their writes (see the buffering above). Where the buffer flushes only at the answer, each key is published once per evaluation; a flush before a local read gives that up for keys written again afterwards. The buffered system terminates on a regression whose equation would otherwise publish twice in one evaluation (keyed_multiwrite_buffered_terminates). That the unbuffered system does not terminate is expected, but neither proved nor evaluated.
  • A verdict is about VIMP. VIMP's integers are machine integers of the declared kinds, signed overflow wraps where C leaves it undefined, and division by zero is defined, so a verdict about a VIMP program does not automatically transfer to a corresponding C program. The arithmetic diagnostics flag the operations where the difference can matter. The theorem is only as meaningful as the semantics it is stated against; the limits section returns to this.

The model

Voblint and Goblint, side by side

Voblint follows the architecture of Goblint, a static analyzer for C programs. Voblint analyzes VIMP instead, a small imperative language with integer variables, globals and recursive procedures (see what it leaves out). What we claim is a simplified, machine-checked semantic model of Goblint's interprocedural, context-sensitive architecture, not a model of its implementation. The vocabulary of locals, globals and side effects follows the FM 2026 tutorial on mixed flow-sensitivity by Goblint's authors.

One row of the table deserves more than a line. Five of the six analyses keep a pointwise state, one abstract value per variable, so it is fair to ask whether the framework works only for that shape. The sixth, the order analysis, shows that it does not. Its carrier is a set of known pairs x ≤ y, and it contains no var_id ⇒ 'a anywhere. Order_Analysis runs this carrier inside the combined state, next to the other analyses, through the same interface as every selectable analysis: it supplies a local specification and proves it sound (ord_spec_sound), the interface the five pointwise analyses reach through their type class. It answers comparisons from the pairs it records, and at an assignment it asks the other analyses how the new value compares with each variable. It is deliberately small: it computes no transitive closure, and calls enter and return with no facts. Together with Interval, it proves checks that neither analysis proves alone (an example).

The fine print

What Voblint can't do

Voblint's soundness theorems hold for a small language under a fixed set of assumptions. This section describes what lies outside them.

How much of C VIMP covers

Goblint analyzes C. Voblint analyzes VIMP, a language small enough that its semantics could be written down and every analysis step proved against it. Hover a region to see what VIMP leaves out.

What the theorems don't promise

That a run finishes

Every soundness guarantee assumes the solve terminates. Proving that in general is out of scope; for intervals, the join-based rules give no answer within a time limit on some programs, and so do entry-state contexts. We expect these solves to diverge, but a timeout does not prove it.

Anything about a program it turned down

A program failing wf_program_compile_input_exec is answered Malformed_Program and never analysed. That is what the Analysed res premise carries: a rejected program gets no guarantee.

Precision

There is no completeness claim. A correct result may still say UNKNOWN for a check that holds.

A counterexample

REFUTED says the check fails in every run that reaches it, not that any run does. An error diagnostic likewise does not prove the point is reachable.

The code around the proof

The parser is generated from one grammar and tested. Isabelle's code generator, the OCaml compiler, wasm and your browser are trusted. Source positions, badges and graph drawings (OCaml rendering, this page) are unverified.

Anything about Goblint's code

Voblint models Goblint's design, and no theorem here speaks about Goblint's OCaml implementation.

Speed

The generated OCaml is slow. Its code is purely functional and written for easy proofs, mostly over association lists, with red-black trees only in a few places.

Facts like x != 5

Goblint's exclusion sets are absent, so no domain records that a variable differs from one constant.

Why this takes so long to prove

The analyzer that runs is a small part of the project. Most of the work went into definitions of what a program means and into proofs that every step of the analysis respects them.

Further reading

Goblint is developed at TUM and the University of Tartu. The groups below run from the oldest ideas this page builds on to the solver proofs it imports. If you read one, read the FM 2026 tutorial on mixed flow-sensitivity, whose vocabulary this page uses.   • Static analysis of arithmetical congruences Philippe Granger · International Journal of Computer Mathematics, 1989 The congruence domain, the component that settles the multiples-of-three example.
