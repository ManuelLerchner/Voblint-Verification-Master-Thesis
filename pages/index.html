Static analysis you can trust, and why

Voblint answers questions about every run of a program without running it, and Isabelle/HOL proves those answers sound. This page covers the idea, how the analysis computes its answer, and why an analyzer's own bugs matter.

Machine-checked theorems connect the source program to the verdicts, and the analyzer in the playground runs the code Isabelle exported from the same definitions.

The output

What does it tell you?

Voblint reads a program and answers questions about it without running it. Every division and remainder is checked for a zero divisor automatically. Anything else you want a verdict on, you write as a check.

The stakes

What if the analyzer is wrong?

Analyzers are programs, and programs have bugs. An unsound one is worse than most: the analyzer reports PROVED for a check that real runs violate, or DEAD for code that runs, and nobody looks again. Mature analyzers track these as their own category; Goblint's issue tracker has a label for them. Below is one of them, replayed with the verdicts it got backwards. The shorthand in the margins is the analyzer's own state, and the next two sections say what it means. What a machine-checked proof rules out comes after them.

The idea

What is abstract interpretation?

A test runs a program on some inputs and watches what happens. Abstract interpretation computes with descriptions of values instead, such as “an integer between 0 and 5”, and keeps each description large enough to include every value a real run could produce at that point. It iterates until the descriptions stop changing. If every value the description allows satisfies a check, every run does.

Many runs in, one region per node out

Here is the same idea on a real program, drawn as the part of its control-flow graph from the first branch on: one node per program point, one edge per step between them. Each run is dropped at the value of x it has at every node it reaches, one dot per node. Switch to the abstract view and the dots give way to the one interval the analysis keeps per node. No interval leaves a dot out, which is soundness. But the runs only ever reach multiples of three, and an interval cannot say so: every band also covers integers no run has. On the left that makes a node look reachable that no run reaches; on the right the guard rules everything out, and the analysis marks the check DEAD. Each check gets a verdict, and each says what the analysis established: PROVED when it shows the check holds in every run that reaches it, REFUTED when it shows the check fails in every such run, DEAD when it shows no run reaches the point at all, and UNKNOWN when the descriptions are too coarse to decide. A check no run reaches can still come out UNKNOWN, as pp4 does here: DEAD says the analysis proved unreachability, not merely that the point is unreachable.

The vocabulary

What an abstract value stands for

Every abstract value names a set of concrete integers, its concretization γ. [−2, 5] names eight of them, even names infinitely many, ⊤ names all of them. Soundness is a statement about those sets: the set the analyzer gives a program point must contain every value a real run has there.

Then the analyzer computes with the sets instead of with integers. Where a run holds x = 7 and executes x = x + 1, the analyzer holds x ∈ [0, 9] and produces [1, 10]: one step of arithmetic standing for every run at once.

The price is precision. A domain has only so many values, so the answer is usually wider than the truth: the real set of values at a point may not be nameable at all, and even when it is, the cheapest route to it may overshoot. Rice's theorem says every non-trivial question about what a program computes is undecidable, so no analyzer answers all of them exactly, and one that always terminates and never lies has to err on the safe side sometimes. Whether erring wide still settles the questions worth asking is what the rest of this page is about.

Five domains, five kinds of description

Sign

Seven values from “nothing” to “anything”. Joining 0 and >0 gives ≥0.

Interval

A lower and an upper bound, either of which may be infinite. Among the four base domains, the only one that needs real widening; Int inherits it through this component.

Parity

Even, odd, or either. Joining even and odd loses everything.

Congruence

A remainder c modulo m. Modulus 0 means exactly the value c.

Int product

All four at once. Its components sharpen one another after every arithmetic operation and every guard, so four weak facts can decide a check.

Four domains, one value: reduction

An Int value describes the integers all four of its components allow. Each component on its own can miss what another one knows, so the product lets them sharpen one another. A sharpening step never changes that set of integers. It only finds a smaller description of the same set, and a smaller description can decide a check that the larger one could not. A component that arrives knowing nothing is not dead weight either: it can be handed something by the others.

A bound that looks wrong

Take an unconstrained n, set x = 6n + 5, and ask for x % 6. You would expect 5, but Voblint reports the interval [−1, 5]. Is this an error in Voblint?

The foundation

A trace, and what makes it local

The soundness theorems on this page are statements about traces. A trace is the record a single run leaves behind: the nodes control passed through, and the store at each of them. One trace is one concrete run, written down. Nothing is approximated yet, and nothing is quantified over yet.

If you have stepped through a program in a debugger, you have watched one being made. Every press of step moves control one node on and leaves the store at whatever the last statement made of it; the line the debugger highlights and the variables panel beside it are one (node, store) pair. A trace is that whole sequence, recorded instead of watched. The one panel a plain sequence throws away is the call stack, and that turns out to be the panel the proofs need.

For a program that is one long stretch of statements, a list of (node, store) pairs is the whole story, and the run below would be exactly that list. Procedures are what makes it not enough.

sum(2) calls dec once and then calls itself, twice over, so the run visits three activations of sum and two of dec, all of them walking that one copy of the graph. That is the collision. Write the run as one flat list and the same node appears again and again with nothing in the list to say which activation each occurrence belonged to.

What “local” means

The shape Voblint actually uses is the second one below, and local is the word for the difference. A local trace is the same steps in the same order, grouped: the debugger's step log, cut along the call stack, so that every step ends up under the activation that executed it. A local trace is about one activation: it holds one trace, its own, and no step of any other activation is on it. What surrounds the activation sits beside that trace instead, and it sits there as local traces of the same kind: the one belonging to the caller that started this activation, and one per callee that has already returned into it. The definition is recursive because the thing it describes is.

The debugger has a name for that cut. Press step into at every call and you get the flat list: the callee's lines scroll past in the same stream as your own. Press step over instead and you get one activation's path, exactly as a local trace records it. The callee still runs and its effect is still in the store when you land, but none of its steps appear on your line. The coloured bars in the figure above are the points where you pressed step over, and the box beneath each bar is the run you stepped over, kept rather than discarded.

The interface

What you can ask a trace

Everything the rest of the page asks of a run goes through six observers, a few lines each on top of the datatype, and the soundness statements read a run only through them.

Start from the type. It is three lines, and with trace named it says its own shape: a local trace is one trace plus the activations around it. 

type_synonym trace = "(cfg_node × store) list"

datatype ltr =
    Root                                         trace
  | Call   (ltr_caller: ltr)                     trace
  | Resume (ltr_current: ltr) (ltr_callee: ltr)  trace

One constructor per situation an activation can be in. Root is main, which nobody called, so it carries a trace and nothing else. Call is an activation that is running and will have to return to its ltr_caller, which it holds. Resume is that same activation after a callee came back: ltr_current is that activation frozen at its call node and ltr_callee is the finished callee, kept whole rather than spliced into the path, which is why a returned call is still one box you can ask questions about.

What the shape buys is one question, one box. “Which runs can be standing at node v, and what does memory hold there?” is answered by looking at the end of one path. On the flat list the same question means scanning an interleaved sequence and deciding, for every occurrence of v, whether it belongs to the activation being reasoned about. The analysis answers per program point — per point and context, once a policy keeps copies of a procedure apart — so that first question is the one every soundness proof in the chain has to ask, and a trace is local precisely so that asking it is a projection rather than a reconstruction.

Grouping by activation rather than by procedure has one more consequence. sum is one procedure and three activations in this run, and the trace keeps all three apart for free, because each is its own box. The analysis cannot afford that: it has to decide in advance how many copies of sum to reason about separately, and that decision is what a context is. The concrete side telling activations apart is the reason the abstract side is allowed to merge some of them and still be checked for it.

It is never built

None of which means the analyzer builds one. It would be a poor thing to build: every trace is finite, but nothing bounds how long or how deeply nested it gets, a recursion has one activation per level, and the set of all of them is infinite as soon as the program reads an unconstrained input.

A local trace is a value in the logic and nowhere else. It exists so that soundness has something to be a statement about, and the proofs quantify over the set without anything ever enumerating it. The evidence is the generated code: of the 9,406 lines of OCaml exported from these theories, the number that mention ltr, valid_ltr, sink_store, caller_of or ltr_collect is zero. The specification does not ship.

The meaning

What a run is: source, graph, local trace

A semantics is a rule for what a program does: given a state, which states may come next. Writing one down is what turns “what the program really does” from an appeal to intuition into a set you can quantify over.

Voblint writes one down three times, because the three things it has to relate are different shapes. A source step (pstep) rewrites a program that is still program text, carrying the store and a stack of caller frames. A CFG step (cstep) moves a position through a control-flow graph, carrying a stack of return points. The third does not step at all. ltr is the local trace of the previous section, and valid_ltr is a rule that says which of those values the graph actually admits: one activation with its whole history in a single value, accepted or not, rather than a move from one state to the next.

Soundness is stated against the third, and the reason is shape. The analysis answers one value per program point, so the claim has to be “at node v, this covers every store a run can hold there”. pstep has no notion of a node at all, so that sentence cannot even be written against it. cstep has nodes, but its state is a whole configuration including the call stack, so standing at v says nothing on its own. Being local is exactly what fixes that: the local traces whose path ends at v are the activations sitting there, one box each, and the store they hold is the one at the end of that path.

The three stacks under that figure are where the semantics differ. At an open call the source keeps a Frame, the caller's store and the variable to assign; the graph keeps those and the node to come back to; a local trace keeps the caller itself, whole, as a field. Soundness has to name a program point, say which stores can be there, and do it one activation at a time, so ask all three the same four questions. A fourth candidate comes for free: trace is a type, and one trace over the whole run rather than one per activation is the flat list from the trace section.

The repeated answers are facts about those stacks. A configuration is a snapshot, so there is no path to read off it. The frames hold the callers' stores, so an activation's own entry store is gone the moment it assigns anything. And a frame names a return point, not a run. The flat trace has the steps but not the grouping, so every answer costs a scan.

The last row is why the proofs use it. Closing a call has to say that this callee came back into that caller, and with the caller in the value the return rule simply writes caller_of callee = Some caller. Against a stack there is no term for the caller's run to bind, and recursion is where that bites. Contexts later read the same two fields: caller_of for the activation that made the call, entry_store for the store it was entered with.

That is the general shape of the choice. A claim can only be as fine as the semantics it quantifies over, so the concrete side has to tell apart at least as much as the abstract side intends to: an analyzer that keeps activations apart needs a semantics that keeps them apart, or the theorem has no way to say what it covers. Picking the finer base costs nothing, because the coarser views are projections of it — ltr_collect drops the activation, activation_collect keeps the key — while a base that has already forgotten cannot be sharpened afterwards.

From one run to one answer per node

The figure above is one run. The analyzer never sees a run: what it produces is a table keyed by program point, with nothing in it about paths, calls or activations (contexts split those keys further, and the section on procedures does that). So the concrete side has to be put into that shape. Take every local trace the graph admits, which is what valid_ltr collects by starting at the entry node, walking an edge, opening a call and closing one. Ask where each trace ends. Keep the store it ended with. 

ltr_collect gs g S v =
  {sink_store t | t. t ∈ valid_ltr gs g S ∧ sink_node t = v}

One bucket per node, holding the stores a real run can be in there. Neither of the other two semantics can be asked for this: over pstep there is no v to index by, and over cstep it can be written, but the only thing there to index it more finely by is the call stack, not the activation.

It is also where the grouping of the last two sections is deliberately spent. A trace had to be local for “ends at v” to mean anything, and then the collection drops the activation and pours all of them into one bucket. activation_collect is the variant that keeps the key, and how much of it to keep is what a context will be.

Soundness asks only for containment, not equality: the answer at v has to cover the bucket beside it, and is free to cover much more.

Which it does, visibly. The run only ever reaches pp2 with n at 2, 1 or 0, and the answer is [-∞, 2]. Two things went into that, and each gets a section of its own later: the three activations of sum were merged into a single entry before anything was computed, and the merged lower bound then kept moving downwards, so the solver stopped chasing it rather than iterate forever. The check at pp10 comes back UNKNOWN on a program whose every run makes it true. Everything from here on is about that gap: how an answer wide enough to be sound is computed at all, and what can be spent to make it narrower.

The computation

From a graph to equations to values

The compiler turns a program into a control-flow graph. The analysis turns that graph into equations. In this single-procedure example that means one unknown per node and one term per incoming edge, each applying that edge's action to the value at its source; procedures will key unknowns by node and context. A solver then finds a value for every unknown. To the rest of the pipeline the solver is a black box: equations go in, one abstract value per unknown comes out.

Watch the compiler take a program apart

The compiler reads a procedure one statement at a time and turns each statement into a numbered node with outgoing edges. Every statement is compiled against the number of the statement after it, so its target is known before it is compiled. The figure replays that walk on the counting loop, with the node numbers and edge labels the real compiler produces.

What an equation is made of: strategy trees

One level down, the solver never sees ⊔ or assume. It sees each right-hand side as a strategy tree, which spells out every step the evaluation takes: QueryL reads a local unknown, QueryG reads a global one, Side contributes a value to a global, and Answer returns the result. A query does not name its next step directly. It holds a function from the value it reads to the rest of the tree, so the solver finds out which unknowns an equation depends on by running it. The trees and the system they make up are the vendored solver's own language: a whole equation system is one function from an unknown to its tree. 

datatype ('x, 'g, 'd) strategy_tree =
    Answer 'd
  | QueryL 'x ('d ⇒ ('x, 'g, 'd) strategy_tree)
  | QueryG 'g ('d ⇒ ('x, 'g, 'd) strategy_tree)
  | Side 'g 'd (('x, 'g, 'd) strategy_tree)

type_synonym ('x, 'g, 'd) eqsT = 'x ⇒ ('x, 'g, 'd) strategy_tree
eqsTone tree per unknown TD solververified, vendored σa value per unknown

Building such a tree directly is awkward. Because a query holds the rest of the tree as a function, every read the generator emits has to be written inside the continuation of the one before it, so the nesting grows with the number of reads and the last step ends up deepest. Voblint therefore generates each right-hand side as a strategy program: a tree still missing the continuation that consumes its result, so it is a function from that continuation to a tree. Two of them compose by handing the first one the second as its continuation, and composing is what do-notation writes down, so the generator states its reads in the order it performs them. sp_compile then closes the last continuation with Answer and a tree falls out.

The two are easy to confuse, so from here on the shape says which one is on screen: a program is written in do-notation, a tree is spelled out with its constructors. Everything the generator builds is a program, and the names say so — dg_spec_edge_program, fold_rhs_program — with sp_compile naming the one step that leaves. 

type_synonym ('x, 'g, 'd, 'a) strategy_program =
  ('a ⇒ ('x, 'g, 'd) strategy_tree) ⇒ ('x, 'g, 'd) strategy_tree

Only the dashed stage is Voblint's, and it is gone before the solver runs, so the vendored correctness proof applies unchanged: the solver receives a tree like any other.

The generator works one edge at a time, then one node at a time. dg_spec_edge_program turns a single CFG edge into a small program: read the unknown at the edge's source, apply the edge's transfer, answer. A node with several incoming edges gets one such program per edge, and fold_rhs_program folds that list into one program, joining their answers: this is where the ⊔ of a join node goes. Compiling the program gives the node's single tree. Publications are held back rather than emitted where they occur, so a node that writes a global ends its tree with one Side carrying the completed contribution (routed_node_rhs_buffered). A node that writes nothing contributes bot, and flush_sides drops that: joining bot into a global changes nothing, and publishing it would still cost the solver an update and a destabilization of that global's readers. Every equation is now a chain of reads ending in an answer: the ⊔ and the assume that the equations above displayed are gone from the top, buried inside the answer where they are just arithmetic on a domain the solver knows nothing about.

What the solver is given

eqs E H B X

The TD solver is demand-driven: it is asked for one unknown, evaluates that unknown's tree, and every QueryL it meets on the way asks for another one, recursively. What it computes is whatever the first question turned out to need, and no more. Voblint always asks the same question, the end of the entry procedure under the root context: 

root_query p = (cfg_exit (prog_cfg p), root_ctx)

That point is the one a terminating run ends at, so asking for it drags in, one query at a time, every point whose value it depends on. What the vendored solver promises is therefore a partial post-solution: it covers the question, its covered set is closed under the dependencies the trees take, and for every covered unknown the tree's answer stays below σ's value there, with its side contributions below σ at the globals they write. That middle clause is only one step deep; part_post_solution_implies_trans_dep_subsumed lifts it to all of them, so everything transitively reachable from the question is inside the covered set.

A point that cannot reach the end is never asked for and stays outside that set. Reading the result there is still defined, and gives bot: 

solved_local_reader vars σ k =
  (case k of Inl vc ⇒ (if vc ∈ vars then locals (σ (Inl vc)) else bot)
           | Inr _ ⇒ bot)

bot is the dead-point element, the same answer the analyzer gives for code it proved unreachable (solved_local_reader_uncovered), and it is sound there for the reason it is sound anywhere: no concrete run reaches that point, so the empty set of stores covers every run that does. Unreachable code therefore costs nothing to analyze rather than having to be recognized and skipped.

What comes back

the black box: widening, and the solver step by step

Why a loop needs widening

A loop can run any number of times, so following it pass by pass may never end. The analysis instead widens: when a bound keeps moving, it jumps straight to infinity, which is safe, and for intervals it stops this climb. It then narrows, using the loop's own guard to pull the bound back. Warrowing combines the two: it widens while a value grows and narrows once it shrinks. Nothing in the equations marks a loop head. The solver finds the widening points itself, on meeting an unknown that is already being computed, and warrows every local unknown that sits at one, whichever rule a run picks for the globals. A domain joins in by instantiating bounded_warrowing. Step through it below.

Procedures

Procedures: how many copies to keep apart

Everything so far had one procedure. A call breaks two assumptions at once: the callee's entry state arrives from somewhere else in the equation system, and several call sites can reach the same copy of it. One mechanism handles both, the solver's side effects, and two settings tune it: how many separate copies of a procedure the analysis keeps apart, and how the values several call sites send into one copy are combined. This section covers the first; the second comes once the system those copies live in is clear. Each changes precision and whether a run finishes, never soundness.

Side effects: writing an unknown you do not own

Every right-hand side so far only read. It queried other unknowns and answered with a value for its own, which is why the walkthrough above could be drawn as one variable moving. The solver allows one more move. A right-hand side can publish into an unknown it does not own: the solver joins the value in, records who published it, and re-runs everyone who had read that unknown. In a strategy tree this is a Side node, and it is the part the walkthrough left out.

Voblint publishes for exactly two reasons. One is the analysis global, the single unknown carrying whatever a domain wants every program point to see. The other is a call: a caller does not write the callee's entry point, it publishes the entry state under a key (Activation_Seed) that the callee's entry reads back. The vendored solver can only side-effect a global unknown, so that key is a global proxy rather than the local unknown Goblint writes with sidel, which is a recorded difference, not an accident.

Both settings act on that one publication. Contexts decide which key a call publishes under, and so how many copies of a procedure exist. Globals decides how several publications to the same key are merged.

What a call adds to one procedure's equations

An analysis does not hard-code what a call does. Three pieces decide it: enter builds the callee's entry state from the caller's, a context policy picks which copy of the callee that state goes to, and combine merges the callee's exit state back into the caller. enter and combine come from the analysis; the policy is a run setting. The framework wires all three into equations the same way for every domain, and each wire carries its own soundness obligation.

The wiring is more local than it sounds. Building the equations is a walk over one procedure's nodes, one equation per node, and a call site is just a node whose contribution happens to publish and query. The walk never goes into the callee. That is why a recursive call needs no special case, and why generating the equations never follows the recursion down: depth is the solver's problem, not the generator's. A real run does go into f, and What a run is: source, graph, local trace steps one through a program with calls.

Context sensitivity: how many copies of a procedure

The walk above was a simplification. Its unknowns were bare program points, so any two calls to f would land in the same copy of it, and the entry states they produce would pile up together. An analysis can be set up to keep those call sites apart. A context is the key a procedure is analyzed under: call sites that produce the same key share one copy of f, call sites that produce different keys each get their own. Picking that key is what this setting does, and there are several strategies to pick from.

c is main's own context. c₁ and c₂ are what the strategy returned at its two call sites, and each reaches exactly two places: the key the call publishes under, and the exit it queries. The rest of the equation the walk wrote stays as it was.

What a solve is

The system nobody can write down

Every figure so far has drawn a handful of equations, which makes a system easy to picture as a list someone wrote out. It is not one. The generator is a function from a program point and a context to a right-hand side, and both arguments range over infinitely many values, so the system has no last equation in any direction. What a run produces is the slice a query reached.

A program point is a cfg_node: a numbered statement, or a procedure's entry or result under a name that is just a string. A context is whatever the policy keys copies by: a call_string, which is a list of call sites, or under entry states the list of abstract values the call binds to the callee's formals, read off the entered abs_state. Neither type is finite, and compiled_routed_eqs_for answers at every pair of them. There is no step at which the equations get built, no table to allocate and no enumeration to bound: the system is already there, and a solve is a walk through the part of it a query reaches.

Five procedures are enough to draw a picture like the one below. This program's call graph is exactly what the arrows in it trace: main calls w and f, f calls itself twice and calls g, and g calls h. w calls itself with a value nothing constrains, so the analysis cannot tell its copies apart and keeps one.

What the source does not say is how many copies of each the analysis will keep, or which keys they get. That is the context policy's business, and it is why the filled cells below are a shape you only see after a run.

Nothing builds any of this. An equation system is an eqsT, and eqsT is a function type: 'x ⇒ strategy_tree, an unknown to its right-hand side. compiled_routed_eqs_for defines one such function, and a function is total: it has a value at every argument of its type. So for every pair of a program point and a context the right-hand side is already there. Nobody constructs it; the solver looks it up, and being infinite costs the design nothing.

Querying it is the only thing that produces anything finite. The solver is handed the system and one unknown, and what comes back is a partial post-solution (part_post_solution): every unknown it stabilised is at least what that unknown's equation computes, over the set of keys it happened to reach. The set is finite because the run stopped, not because the system was ever small.

Getting a value back is not itself the guarantee. Read a key the solver never touched and you get bottom, the same bottom a genuinely dead point answers with, and nothing in the value tells the two apart. The theorem does: soundness is stated over the stabilised keys, so an answer is worth something exactly when its key is one of them.

Shared state

Globals: what several callers write into one entry

The two settings move different axes of the same picture. Context sensitivity decides the columns: which unknowns exist, and how many copies of a procedure you get. This one decides what a cell holds where several writers land on one key. It never adds a key and never removes one, so it can stop a value climbing forever and cannot stop the copies themselves multiplying.

Where the writes meet

The name is the solver's global unknowns, not VIMP's global declarations. The two do meet at one point: a program's globals sit in the state a call publishes, so they cross a call through a solver global. That channel is the one the section above drew as a dashed arrow, a call site writing the callee's entry key and the callee's own entry equation reading it back. Those entry keys are what the rest of this section measures, and this setting is what happens where several writes meet at one of them.

Three of the four programs the guide table further down measures, in one file. The fourth is a recursion whose argument never stops climbing, and it cannot sit beside them: whether that one finishes at all is the first thing this setting decides. Each call site is lettered, because a site is what writes a key: A and B both write p's entry, C is g's only writer but publishes more than once, and D and E both write s's.

Every key here takes several contributions, so all four settings have something to do, and they do not agree. Warrow widens p's and g's entry away and loses both checks. Warrow per origin keeps those two and loses s. Join and Join per origin keep all three, and neither of them finishes on a recursion whose argument climbs, which is why neither is the default. The four-program table further down is those runs.

Widening only helps where a key is shared, though. Run f(x) { f(x + 1); } from f(0) at --context none and Warrow finishes with x = [0, +∞], because one key takes every contribution and widening cuts the climb off. Run the same program under entry-state contexts and no setting here finishes: each new argument is a new context, so it is a new key with one writer, and there is nothing for any of these rules to widen against. Copies are the context setting's problem.

One key, four rules

What a site sends is the state its call binds the callee's parameters to, so [0, 3] is one site saying the parameter arrives somewhere in that range. What the rule makes of them is a single value: the callee's entry, the state it is analysed from and seeds its own calls from in turn.

One site can send several times. A right-hand side is not run once; the solver re-evaluates it whenever an unknown it reads has moved, and each re-evaluation publishes again at the same key from the same origin. Site C above does that each time the loop head's value moves, which is a few rounds however many turns the loop runs for. A contribution comes back smaller when narrowing has pulled a widened value down and the site is recomputed from it.

Below, A and B are two writers at one key. The numbers are not the program's; they are picked so that A sends three times, smaller and then larger, which is what it takes to tell all four rules apart: step 2 separates Warrow from the rest, step 3 Join from Join per origin, step 4 Join from Warrow per origin. They are intervals because the rules hold for any domain with a join, a widening and a narrowing, and Interval is the one where the widening does something the join does not: Sign and Parity are short enough lattices that their widening is defined as the join.

Why not always Join, then

Because its cost follows the chain. Joining never widens, so a value that climbs is walked one step at a time and the solver needs a round for each; widening takes the same chain in one step. On f(x) { if (x < N) f(x + 1); } from f(0) every rule proves x <= N, but as N goes from 64 to 4096 the two joining rules go from 5 ms to about 240, while the two widening rules stay at 4. Take the bound away and that growth has no end, which is the no answer in the table below.

Which Globals setting should you pick?

No setting is best everywhere. They trade how quickly a growing value is cut off against how much a merged value forgets. Nothing proves any of them terminates on every program: Voblint assumes termination per program, so a bad choice shows up as a run that never finishes, not as a wrong answer.

Start with Warrow

The playground's starting point. Widening is what stops a recursive call whose argument keeps growing. It cannot stop entry-state contexts from multiplying, though: those need context None or a call string.

UNKNOWN with several callers?

Try Warrow per origin. It widens each call site's contribution on its own, so one caller's growth is not blurred into a jump to infinity for all of them. It is not always better: see the last row below.

Join and Join per origin on intervals

Precise when a procedure receives finitely many values, but they never widen: a call chain that keeps growing an argument makes the run spin forever.

If a run does not finish

The playground has no timeout; the command-line analyzer takes one with --timeout. Press Cancel, or change any setting, then pick Warrow or Warrow per origin, and switch entry-state contexts to None or a call string.

Both settings at once

Run every combination of the two settings on the program above and the axes separate cleanly. Cost moves down the rows only: the solved graph has 24 nodes with no contexts, 34 at either call-string depth and 38 under entry states, and within a row that count never moves, because this setting adds and removes no unknown. Precision moves both ways, and the coarser the context the more damage a widening does — Warrow proves one of the three checks with no contexts and all three once entry states keep the writers apart, while both joining rules prove all three everywhere. The cheapest fully precise cell is None with Join, which is also the combination that never finishes on a recursion whose argument climbs.

A call that never stops calling

Both settings meet in recursion. f(x) calls f(x + 1) forever, so real runs wind outward on an endless spiral: f(0), f(1), f(2), each turn wider than the last. The analysis has to describe every turn with finitely many contexts, and whether it can depends on the settings: Join and entry-state contexts follow the spiral and never finish, warrowing cuts across it. Switch to the same function stopped at x = 10 and every setting finishes.

The guarantee

What does “verified” mean?

The congruence bug that opened this page is the kind of mistake a proof rules out: VIMP's % is c_mod, and the congruence domain has to prove that c_mod i j lands inside γ of whatever it answers, which an operation that rounds the wrong way cannot do. Voblint's analysis is written in Isabelle/HOL, and theorems there state that, once the solve finishes, its answer covers every store a real run can have. Isabelle checks each step of those proofs down to the axioms of its logic.

Correct with respect to what?

Every theorem here assumes one thing about your program: what a run of it does. That is pstep and the operators it runs on, down to c_mod taking its sign from the dividend, as C does. Isabelle checks that the analyzer's answers cover every run those definitions admit. It cannot check that they are the definitions you meant, and whether pstep is really what a C-like language does is a reading task no proof discharges.

The graph and trace semantics are not on that list: they are reached from pstep by proof (source_reaches_ltr_collect).

What is left to read is 6 theories, 963 lines out of the 62,098 in src/, with pstep's 14 rules among them: VIMP_Syntax, VIMP_Expr, VIMP_Special, VIMP_Globals, VIMP_Program and VIMP_Proc. Everything else, the compiler, the equation generator, the solver, the five domains and the result table, the kernel has already checked against them. Review is bounded by the size of the semantics, not by the size of the analyzer.

Where the proof starts and stops

A proof covers a precise statement about precise definitions. Whatever the statement does not mention is trusted: it has to be correct for the guarantee to reach you, but nothing here proves it.

From Isabelle to your browser tab

The analyzer you run in the browser is not a reimplementation of any of this. Isabelle exports the proved definitions as OCaml, the OCaml is compiled to WebAssembly, and a background worker started by the playground calls it. The green box above is what travels.

The argument

The proof chain: each set inside the next

Soundness is a chain of set inclusions. At one program point, start from the stores real runs have there and widen step by step: the stores the graph's local traces reach, then those traces split by context, then what the solver's answer concretizes to. Each link is its own theorem, and the analysis may lose precision at every link but never a store. One more step at the end turns the last set into the badge you see. Below, the chain is drawn for n at pp0, the if (n < 2) of this one: 

fun f(n) {
  if (n < 2) {
    return 1;
  }
  r = f(n - 1);
  return n * r;
}

fun main() {
  x = f(2);
}

main calls f(2), which calls f(1), so two runs reach pp0: one with n = 2 and one with n = 1.

Take a pillar away

The chain is a bridge from real runs to the verdicts, and five facts hold it up: two theorems and three obligations the analyzer has to discharge. Remove one to see which answers stop being covered.

The model

Voblint and Goblint, side by side

Voblint follows the architecture of Goblint, a static analyzer for real C programs, and simplifies wherever a proof would otherwise have to model all of C. The project's own register of differences says what the claim is: “a simplified, machine-checked semantic model of Goblint's interprocedural context-sensitive architecture”, and not the exact implementation. Its vocabulary of locals, globals and side effects, and many of this page's examples, follow the FM 2026 tutorial on mixed flow-sensitivity by Goblint's authors.

One row above understates itself. Every shipped domain keeps a pointwise state, one abstract value per variable, so it is fair to ask whether the framework only works for that shape. It does not, and there is a witness: Rel_Order_Domain carries a set of known pairs x ≤ y instead — no vname ⇒ 'a anywhere in the carrier — and interprets sound_dg_spec_core with no change to the framework. It is a deliberately useless analysis, precise only on a guard and forgetful everywhere else. Its job is to be relational and still fit.

The fine print

What Voblint can't do, and why proving is hard

A proof is only as wide as its statement. Voblint's soundness theorems hold for a small language under a fixed set of assumptions; this section is about what sits outside them.

A small island in a large language

Goblint analyzes C. Voblint analyzes VIMP, a language small enough that its semantics could be written down and every analysis step proved against it. Hover a region to see what VIMP leaves out.

What the theorems don't promise

That a run finishes

Every soundness guarantee assumes the solve terminates. Proving that in general is out of scope; for intervals, the join-based rules can run forever, and entry-state contexts can under any rule.

Anything about a program it turned down

A program failing wf_program_compile_input_exec is answered Malformed_Program and never analysed. That is what the Analysed res premise carries: a rejected program gets no guarantee.

Precision

There is no completeness claim. A correct result may still say UNKNOWN for a check that holds.

A counterexample

REFUTED says the check fails in every run that reaches it, not that any run does. An error diagnostic likewise does not prove the point is reachable.

The code around the proof

The parser is generated from one grammar and tested. Isabelle's code generator, the OCaml compiler, wasm and your browser are trusted. Source positions, badges and graph drawings (OCaml rendering, this page) are unverified.

Anything about Goblint's code

Voblint models Goblint's design. No theorem here speaks about Goblint's OCaml implementation.

Speed

The generated OCaml is slow. Its code is purely functional and written for easy proofs, mostly over association lists, with red-black trees only in a few places.

Facts like x != 5

Goblint's exclusion sets are absent. Over unbounded integers, joining 5 and 7 has no least upper bound among them, so exclusion sets cannot form the lattice these domains require.

Why this takes so long to prove

The analyzer that runs is the visible tip. Most of the work is underneath: definitions of what a program means, and proofs that every step respects them.

The formalization in cross-section

The iceberg counts volume; this counts structure.
