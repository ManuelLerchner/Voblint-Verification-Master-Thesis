Profiling

What the verified analyzer costs

Every regression fixture, run under every abstract domain and context policy, natively and in the browser's WebAssembly build. The numbers are measurements on one machine: they show where time and memory go, and they prove nothing about programs outside the corpus.

Cost and precision

Which configuration pays for its precision?

Every domain can run under several context policies. None analyses each procedure once for all its calls; entry-state analyses it once per distinct entry state; call strings with k = 1 once per calling site. More contexts can prove more, and cost more. This plot puts the two side by side for every combination the snapshot measured.

How this was measured
  • Each fixture runs under every configuration with the CLI's other defaults (globals warrow, Int refinement to a fixpoint, flow-sensitive program globals). A fixture's own PARAM header is ignored, so every configuration sees the same programs.
  • Time is the CLI's own measurement around the solve (--timing), the median of runs. Process start-up, parsing and printing are not in it, so a sum over the corpus is solving alone.
  • A check counts as proved when the CLI prints PROVED for it. The denominator is every check in the corpus once, taken as the most checks any configuration reported for a fixture. A configuration the CLI rejects for a fixture, or one that runs past  s, proves nothing there.

Corpus profile

How fast is a typical fixture?

Totals hide whether one fixture or all of them are slow. A quantile plot, as SV-COMP uses for verifiers, sorts the fixtures by run time: the curve's height at x is the run time of the x-th fastest fixture. A flat curve means uniform cost; a sharp rise at the right end means a few fixtures dominate.

Scaling

How does recursion depth scale under entry-state contexts?

Under entry-state contexts, every distinct abstract argument a recursive procedure is entered with becomes its own context. The program below recurses n levels deep. A domain that tells the arguments apart, such as Interval, therefore creates n + 1 contexts of h, while one with few abstract values, such as Sign, creates the same few at every depth. Growing n measures how the solver scales in the number of contexts, the case that overflowed the playground's stack before the CPS build. 

fun h(i) {
  if (i == 0) { return 3; }
  r = h(i - 1);
  return r;
}
fun main() {
  x = h(n); __voblint_check(x == 3);
}

How this was measured
  • Every domain under entry-state contexts. Each point is the median of runs of the CLI's own solve timing; peak RSS, in the tooltip, is the whole process's, from the system's time command. A domain's sweep stops at the first n whose run passes  s or fails; the reading names where.
  • Evaluations: the number of eq events in a separate traced run's JSON Lines trace, one per evaluation of an unknown's right-hand side. Tracing slows the run; the repository's tracer gate checks that a traced run gives the same answer as an untraced one.
  • WebAssembly: the playground's bundle under Node with a 512 KiB stack and no trace, timed by the analyzer around the same solve, median of runs.

Data structures

Which program size breaks the generated data structures?

The generated code keeps sets and maps as lists. A membership test scans the list, a union inserts element by element, and removing duplicates compares every pair. Each of the families below grows one size of a program and keeps the rest small, so the dimension that drives one of these lists shows up as solve time that grows faster than the solver's work.

Family What grows Context policy Largest n Time exponent Evaluation exponent Gap

Isabelle has libraries for faster sets and maps. The Collections Framework (Lammich and Lochbihler) refines abstract sets and maps into verified balanced trees and hash tables, and Light-weight Containers (Lochbihler) replaces the list-based default of code generation with such structures. Either needs only targeted replacements in the code setup and no change to the soundness proofs.

How this was measured
  • Each family is a generated VIMP program with one size parameter n: as many variables, straight-line statements, globals, call sites, procedures in a chain, sequential loops, or recursion levels. Every program ends in a check the analyzer proves, so each run does the full work of a real analysis.
  • Call sites run twice. Call strings with k = 1 give every site its own context, while entry-state contexts merge the identical calls into one, which separates the cost of contexts from the cost of call sites.
  • Times are the CLI's own solve timing, the median of runs; evaluations come from a traced run, as in the recursion plot. Exponents are least-squares fits on log–log axes, for time from n = 100 up, where start-up no longer dominates, and for evaluations from n = 20 up, since they are exact counts and tracing reaches the time limit sooner. A gap of about 1 or more means each evaluation gets roughly n times more expensive, the signature of a linear scan inside the solver's loop.
  • The family with the largest gap also gets a CPU profile, listed with the others in the section below.
