section ‹The combined state of the registered analyses›

text ‹
  Every registered analysis owns one field of the combined state. This theory names
  the analyses, lays out the fields, and states for each analysis how its field runs,
  what it describes, how it reads back and answers queries, and where it starts.
  Nothing here is proved beyond citing each analysis's own registration; the
  combination and its soundness are in ‹MCP_Analyses›.

  A new analysis adds a constructor to each datatype below, a field to the product
  types, and one equation to each function that splits on the analysis.
›

datatype analysis_domain =
    Sign_Analysis
  | Interval_Analysis
  | Parity_Analysis
  | Int_Analysis "refine_mode"
  | Congruence_Analysis
  | Order_Analysis

lemma analysis_domain_cases:
  obtains "a = Sign_Analysis"
  | "a = Interval_Analysis"
  | "a = Parity_Analysis"
  | "a = (Int_Analysis Refine_Fixpoint)"
  | "a = (Int_Analysis Refine_Once)"
  | "a = (Int_Analysis Refine_Never)"
  | "a = Congruence_Analysis"
  | "a = Order_Analysis"
  by (cases a) (metis refine_mode.exhaust)+

subsection ‹One value type wide enough for every analysis›

text ‹
  A run result crosses the dispatcher without its caller knowing which analysis
  produced it, so every published value in it has one type: a tagged union with one
  constructor per registered analysis. Each is rendered by its own analysis and listed
  by an injective key, so no printer decides which contexts are listed.
›

datatype abstract_value =
    SignValue "sign"
  | IntervalValue "ivl"
  | ParityValue "parity"
  | IntDomValue "int_dom"
  | IntDomOnceValue "int_dom"
  | IntDomNeverValue "int_dom"
  | CongruenceValue "congruence"
  | OrderValue "(vname × vname) list option"

subsection ‹Fields›

  The combined state nests binary products, so field ‹n› sits one
  ‹pright› deeper than field ‹n - 1›. The last field is the
  right component of the innermost product.
›

subsection ‹Each analysis on its own field›

text ‹
  What the analyzer runs of one analysis: how its field steps, whether it is live or
  empty, how its published value answers a query and is displayed, and the values it
  keys a callee by. ‹registration_of› is the one function that splits on
  the analysis at runtime. The concretizations are proof-only and are not part of it:
  a record the exported code builds holds executable values only, so the emptiness
  test on published values is proof-only as well.
›

subsection ‹Where each field starts, and what it keys a callee by›

text ‹
  The entry state starts every active field at its analysis's own entry state and
  every other field at its bottom. A field no active analysis runs is never read, and
  keeping it at bottom makes the solver's joins, widenings and comparisons on it
  constant-time. Under the entry-state policy a callee is keyed by what the active
  fields key it by; a field no active analysis runs keys nothing.
›

definition mcp_init :: "analysis_domain list ⇒ mcp_st" where
  "mcp_init as = Product (if Sign_Analysis ∈ set as then Lifted cinit_sign_st else ⊥)
    (Product (if Interval_Analysis ∈ set as then Lifted cinit_ivl_st else ⊥) (Product
    (if Parity_Analysis ∈ set as then Lifted cinit_parity_st else ⊥) (Product (if
    (Int_Analysis Refine_Fixpoint) ∈ set as then Lifted cinit_int_dom_st else ⊥)
    (Product (if (Int_Analysis Refine_Once) ∈ set as then Lifted cinit_int_dom_st else
    ⊥) (Product (if (Int_Analysis Refine_Never) ∈ set as then Lifted cinit_int_dom_st
    else ⊥) (Product (if Congruence_Analysis ∈ set as then Lifted cinit_congruence_st
    else ⊥) (if Order_Analysis ∈ set as then (⊤ :: relc) else ⊥)))))))"
