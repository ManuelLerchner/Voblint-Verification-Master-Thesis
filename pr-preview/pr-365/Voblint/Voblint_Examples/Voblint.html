section ‹Certified pipeline›

text ‹
  ❙‹What this development proves.›  An end-to-end soundness proof for a Goblint-style abstract
  interpreter for VIMP, machine-checked from the source operational semantics to the
  ∗‹computed› analysis result.  The whole pipeline, each arrow a theorem:

  ▩‹
    source execution
      -> procedure-aware CFG execution
      -> activation trace
      -> collecting semantics
      -> D/G equation system
      -> verified side-effecting solver
      -> abstract post-solution
      -> source-level soundness
  ›

  Each arrow is justified independently.  Compiler simulation preserves source
  behavior.  Forgetful trace projections introduce no abstract states.  Transfer,
  join, routing, and widening occur only on the abstract side and are justified by
  containment in the corresponding concretization.

  ❙‹Where the chain ends.›  At the operation the CLI actually calls and code
  generation actually exports, not at an internal solved system.
  @{thm [source] run_voblint_source_sound}, in
  \<^theory>‹Voblint_CLI.Analysis_Certified›, says: run the source program, stop
  wherever you like, and ask any configuration --- a list of active analyses, a global
  update rule, a context policy and a placement of program globals --- for a report.
  There is a graph node and frame stack for where you stopped, some state the report
  holds at that node describes your store, and every definite verdict the report gives
  there holds of that store.

  Under a context policy the report holds one state per point ∗‹and› context.  A
  store reaching a point then lies in the state filed under at least one context its
  own call history is admitted at --- exactly one for a call string, possibly several
  under entry-state routing; quantifying over every covered context would be false,
  since another activation's state need not describe this store. Joining the states
  of all contexts at the node gives one state that does describe it
  (@{thm [source] run_voblint_source_sound_joined}), at the price of precision.

  A caller owes nothing beyond the answer itself.  \<^const>‹run_voblint› solves with the
  executable solver, which answers only where the solve terminates, so an analysed
  answer carries termination; coverage of the solve follows from the solve, and a
  malformed program answers ‹Malformed_Program›.  The context policy is read in one
  function, \<^const>‹analysis_report_of›, and its soundness is proved by one case split.

  \<^theory>‹Voblint_Examples.Example_End_To_End_Certificate› is that theorem
  with nothing left to assume.  It fixes one program at the product domain, a
  call-string context of length one and always-join globals, evaluates
  the answer, builds the source run step by step, and reads the listed
  \<^const>‹Check_Proved› check off the conclusion.
›

section ‹Flagship theorems›

text ‹
  Each theory cited here compiles a source program, generates its D/G equation system,
  ∗‹computes› a solution with the verified solver (‹by eval›), and proves a soundness
  theorem about that computed result.  The session READMEs carry each family's full witness
  inventory; this index names only the headline results along three axes: which domain, which
  context policy, and how far the product domain's components refine each other.

subsection ‹One domain, the whole pipeline, monovariant›

text ‹
  One flagship per selectable domain, all on the same generator and vendored solver.  Only
  the lattice differs.

  ▪ @{thm [source] flagship_source_run_sound}
    (\<^theory>‹Voblint_Examples_Interval.Example_Interval_DG_Flagship›) bounds actual source
    runs of an interval counting loop.
  ▪ @{thm [source] dgEx_source_run_sound}
    (\<^theory>‹Voblint_Examples_Sign.Exec_Sign_DG_Run›) is the same bound for Sign, solved
    with the always-join update rule.
  ▪ @{thm [source] parity_source_run_sound}
    (\<^theory>‹Voblint_Examples_Parity.Example_Parity_DG_Flagship›) is the Parity instance on
    an even-step loop.
  ▪ \<^theory>‹Voblint_Examples_Congruence.Example_Congruence_DG_Run› computes exact residue
    classes at the exit of a straight-line program.
  ▪ \<^theory>‹Voblint_Examples_Int.Exec_Int_DG_Run› runs the reduced product of Sign,
    Interval, Parity and Congruence.  @{thm [source] dgExI_never_ne_once} separates
    \<^const>‹Refine_Never›, which narrows only the Parity and Congruence components, from
    \<^const>‹Refine_Once›, whose one reduction round reaches the exact singleton.  Refinement
    is legal because \<^const>‹int_reduction_step› preserves the concretization while
    descending the order.
›

subsection ‹Context sensitivity: three storage policies for one axis›

text ‹
  All three are certified against the same activation-indexed semantics, bounding
  \<^const>‹activation_collect› at every ‹(node, context)› pair.  They differ only in what a
  context ∗‹is›.

  ▪ ❙‹Monovariant.› @{thm [source] twice_source_run_sound} analyses ‹twice›, whose single
    procedure is called from two sites with different arguments, under one shared entry state.
  ▪ ❙‹Entry state›, the entered abstract value of the callee's formals (Seidl et al.,
    ∗‹Mixed Flow-Sensitive Static Analysis›, FM 2026, Example 8).
    @{thm [source] twice_activation_collect_sound} keeps the two calls of ‹twice› in the
    distinct contexts ‹[3,3]› and ‹[10,10]›, where the monovariant baseline joins them;
    \<^theory>‹Voblint_Examples_Interval.Example_Interval_Source_Ctx› lifts that bound to
    source runs at each activation's own context.
  ▪ ❙‹Call string›, a bounded record of the call sites that led to the activation
    (FM 2026, Example 7).  @{thm [source] sign_nest_1_activation_collect_sound} and
    @{thm [source] sign_nest_2_activation_collect_sound} run one ‹nest› program at
    ‹k = 1› and ‹k = 2›; on Sign, whose computed solution is exact,
    @{thm [source] sign_k2_strictly_more_precise_than_k1_at_g} shows the longer string
    strictly more precise at ‹g›'s entry.

subsection ‹Activation-trace concrete semantics›

text ‹
  \<^const>‹valid_activation_trace› represents one procedure activation and its ancestry.
  \<^const>‹Root› starts main, \<^const>‹Call› records an immediate caller, and
  \<^const>‹Resume› continues that caller after its callee reaches the matching
  result node.  Structural caller links distinguish nested and recursive activations
  without placing an unbounded stack in CFG nodes.

  \<^const>‹node_collect› forgets the activation structure and collects stores by
  node, while \<^const>‹activation_collect› keys the same collection by the
  structural activation context.  Both contain only stores from valid activation traces.
›

subsection ‹Procedure-aware source and CFG›

text ‹
  Procedures receive fresh local state and inherited globals.  A call frame stores
  the caller state and optional destination.  Explicit return enters unwinding,
  which skips the remaining commands in that activation and resumes the immediate
  caller.  Main has no caller and accepted programs therefore require it to terminate
  by ordinary fall-through.

  CFGs use explicit \<^const>‹FunctionEntry› and \<^const>‹FunctionResult› nodes.
  The \<^const>‹intra› relation carries local transfers and matching returns.  The
  \<^const>‹calls› relation carries call-site, callee-entry, and continuation data.
  Compiler certificates expose the node ownership and range separation needed by
  the source/CFG simulation.
›

subsection ‹Equations, D/G routing, and solver›

text ‹
  Every node equation joins ordinary predecessor flow, callee-entry flow, and
  caller/callee combination.  Executable equations and their soundness proof use
  the same contribution families.

  The D/G interface separates local flow-sensitive facts from information published
  through global side effects.  Analyses choose the two carriers, routing operations,
  and context keys.  Every domain instance --- Sign, Interval, Parity, the ▩‹int_dom›
  product, and the relational carrier --- shares the one verified side-effecting top-down
  solver and the one collecting-soundness infrastructure.
›

subsection ‹Executable witnesses›

text ‹
  The interval and Sign flagships compile source programs, generate their D/G
  equations, execute the verified solver, and certify the computed post-solutions.
  The ‹twice› program calls one procedure from two sites; its activation-sensitive
  interval analysis keeps the two call contexts separate.  Recursive examples test
  structural activation nesting independently of that repeated-call witness.

  The exported analyser returns its solved result as data; the text report, GraphViz
  drawings and report pages are built from that data outside this development, so no
  rendering is part of any soundness claim.

  ❙‹How the development is laid out.›  One Isabelle session per architectural
  layer, and the ROOT graph is what keeps the layering honest: a theory cannot reach
  past its session's declared ancestors, so a boundary claimed in prose is also
  enforced by the build.  ▩‹Voblint_CFG› never sees the compiler, which is why every
  D/G soundness endpoint below holds for an arbitrary CFG rather than only for a
  compiled one; ▩‹Voblint_Solver› never sees a CFG; ▩‹Voblint_Framework› never sees a
  concrete domain.

  Two layers are families rather than single sessions.  Every abstract domain has its
  own analysis session over the shared ▩‹Analyses/Shared/› chain --- Sign, Interval,
  Parity, Congruence, the ▩‹int_dom› product, and the relational carrier --- and its
  own example session over that, so a domain's witnesses cannot quietly depend on a
  sibling domain.  ▩‹Voblint_CLI› is where they meet again, because the dispatcher has
  to see all of them, and a downstream codegen session exports it.  This theory is the
  most downstream file in the development: it imports the CLI and every flagship, so
  anything it names has actually been built.

  The index below separates the proof spine from executable frontends and research
  witnesses.

    ▪ @{theory Voblint_VIMP.VIMP_Notation} --- ▩‹γ (...)› quotation bracket for examples.

    ▪ @{theory Voblint_Framework.DG_Indexed_Generator} ---

  ❙‹4. Concrete domains.› One analysis session per domain, all over the shared

    ▪ @{theory Voblint_Analysis_Sign.Sign_Transfer} /
      @{theory Voblint_Analysis_Sign.Sign_Analyses} --- the seven-element Sign

    ▪ @{theory Voblint_Analysis_Interval.Interval_Domain} /
      @{theory Voblint_Analysis_Interval.Interval_Analyses} --- intervals over

    ▪ @{theory Voblint_Analysis_Parity.Parity_Domain} --- even/odd.

    ▪ @{theory Voblint_Domain.Congruence_Lattice} ---

    ▪ @{theory Voblint_Domain.Int_Lattice} /

    ▪ @{theory Voblint_Analysis_Sign.Sign_Analyses} --- the routed

  ❙‹5b. Solved results and reports.› What a finished analysis ∗‹is›, before anyone
    renders or dispatches it.
    ▪ @{theory Voblint_Framework.Solved_Table} --- the
      domain-generic table: a covered key set of
      \<^typ>‹pp × 'ctx› pairs plus a total lookup.
      ▩‹wf_solved_table› requires finitely many keys and

    ▪ @{theory Voblint_Framework.Check_Report} and

    ▪ @{theory Voblint_CLI.Analysis_Config} --- the selection surface:

  ❙‹6. End-to-end theorems.› Headline soundness and the source bridge.
    ▪ @{theory Voblint_Result.Source_Activation_Sound} --- the
      source-adequacy bridge. A reachable VIMP source configuration produces a
      \<^const>‹valid_activation_trace› trace
      (▩‹source_run_has_activation_trace›), bounded at its activation

    ▪ @{theory Voblint_Result.DG_Live_Unknowns} --- the endpoints of a routed
      analysis whose route is a function of the call site, the unit context
      among them; they are what every flagship and codegen entry point applies: one
      ▩‹solve_c ... ≠ None› fact in, source-level soundness out.
      Solver correctness, executable-to-pure commutation, post-solution
      transport, and D/G collecting soundness are discharged inside. It is
      partial correctness: the caller supplies that the solver
      ∗‹returns›, typically ⬚‹by eval›.
    ▪ @{theory Voblint_CLI.Analysis_Certified} --- one soundness statement for
      every configuration the dispatcher answers with a report
      (@{thm [source] run_voblint_source_sound}), and the dead-check and
      arithmetic-error guarantees at the same entry point
      (@{thm [source] run_voblint_dead_check_unreached},
      @{thm [source] run_voblint_arithmetic_refuted}).
    ▪ @{theory Voblint_Examples.Example_End_To_End_Certificate} --- that
      statement instantiated at one program, with its answer evaluated.

  ❙‹7. Examples and witnesses.› Executable demos, precision
    witnesses, and tooling. The five domain flagships

    ‹Example_Parity_DG_Flagship›, ‹Example_Congruence_DG_Run›,

    ‹Example_Interval_Source_Ctx›.  Analysis results on concrete programs are pinned
    by the VIMP regression corpus under ▩‹tests/regression›, which runs the
    generated analyzer in seconds.
    ▪ @{theory Voblint_Analysis_Int.Int_Refinement_Control} closes with the
      refinement witnesses: \<^const>‹Refine_Once› stops short of the fixpoint
      (@{thm [source] refinement_once_not_fixpoint}), and refining after
      ‹narrow› would break the solver's bracket

  ❙‹9. The CLI: configuration and code generation.›
    One public operation over every activation list, update rule and context policy,
    running the active analyses as one component of the shared pipeline, and exported
    to OCaml.
    ▪ @{theory Voblint_Solver.Globals_Rule} --- the rule that merges contributions to a
      side-effected global, as a value: one solver interpretation serves all four, and

    ▪ @{theory Voblint_CLI.Analysis_Run} --- \<^const>‹run_voblint›, the one operation
      code generation exports: a configuration of analyses, a global update rule and a

      is a projection outside the theorems. ▩‹dispatch_demo_interval_precise› pins one
      program's answer ▩‹by eval›, and a hand-written OCaml driver under

    ▪ @{theory Voblint_CLI.Analysis_Run_Sound} and
      @{theory Voblint_CLI.Analysis_Run_Ctx_Sound} --- one soundness table per context
      policy (@{thm [source] mcp_rule_table}, @{thm [source] mcp_es_rule_table},
      @{thm [source] mcp_cs_rule_table}), each stated for an arbitrary activation list
      and update rule, over the registrations of
      \<^theory>‹Voblint_CLI.MCP_Analyses›.
      @{theory Voblint_CLI.Analysis_Report} reads a report through ‹ℛ⇘res⇙ v› and
      \<^const>‹verdict_stores› and proves, by one case split over the tables, that

      @{theory Voblint_CLI.Analysis_Certified} states
      @{thm [source] run_voblint_source_sound} and
      @{thm [source] run_voblint_check_sound} once for every configuration.

      ❙‹What the proof attaches to.› ▩‹export_code› translates the executable
      equations of \<^const>‹run_voblint› and everything it transitively calls, down to the
      solver itself. It is not proving one function and exporting a different,
      hand-written one: the generated operation is a translation of the same equations
      @{thm [source] run_voblint_source_sound} is proved about. That theorem asks for no
      termination premise: an analysed answer exists only where the executable solve
      returned. It is partial correctness; nothing proves the solve returns on every
      program. \<^theory>‹Voblint_Examples.Example_End_To_End_Certificate› evaluates
      the answer for one program and applies the theorem to a concrete run.

  every step machine-checked, from source to a soundness theorem over the
  ∗‹computed› analysis result:

    ▪ VIMP source ▩‹compile_prog› to a CFG;
    ▪ the generic D/G generator ▩‹compiled_routed_eqs_for› emits the equation system;
    ▪ the verified solver ∗‹computes› a solution (▩‹solve_c ... = Some sigma›, ▩‹by eval›);
    ▪ the endpoint ‹interval_rule.fun_route_source_sound›
      (@{theory Voblint_Result.DG_Live_Unknowns}, the routed analysis at the unit
      context) bundles solver correctness,
      executable/pure commutation,
      post-solution transport, and D/G collecting soundness into one
      application, bounding ‹𝒞⇘𝒢,g,S⇙ v› at every program point.

  ❙‹Soundness spine.› The context-sensitive analyses converge on one native
  interface, the carrier-opaque ▩‹analysis_contract›; every domain is one of its
  instances, and context slicing is factored through

  and call-string routings stay functional (\<^const>‹context_policy_of_fun›), while
  entry-state routing genuinely admits several contexts per call. There is one
